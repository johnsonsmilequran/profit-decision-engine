# r2-pm-reviews-others.md

## PM 评 架构师章节

[需要改] §4.2、§6.1、§6.6 只描述由待处理申请进入角色配置的身份

原文：「`SCOPED_IDENTITY ||--|| ACCESS_REQUEST : has lifecycle`」「Admin->>ACCESS: 打开最老待处理身份」

问题：F09 不只要给首个待处理用户授权，还必须让 Admin 对上线前已经存在的运营/运营主管映射执行变更、停用和恢复。当前模型把身份详情入口绑定在 `ACCESS_REQUEST`，流程也只从待处理列表进入，已有有效角色但从未产生申请的用户可能无法被发现和管理，US-F09-02 闭环不成立。

建议：明确 `SCOPED_IDENTITY` 可在没有待处理申请时由既有角色映射建立或投影；补充“已授权/已停用身份列表或检索 → 统一身份详情 → 变更/停用/恢复”的流程。迁移或投影不得重建业务身份、改变当前角色或撤销既有有效会话。

[冲突] §4.2 的一对一申请关系与既有授权用户不兼容

位置 A：「`SCOPED_IDENTITY ||--|| ACCESS_REQUEST`」（架构师）

位置 B：「Admin 可修改、停用和恢复业务角色映射」（`scene-anchor.md`，不限定该身份必须先有申请）

问题：强制一对一会为既有授权用户虚构一条“待处理申请”，或使其无法进入统一生命周期；两者都会改变历史事实。

建议：把申请定义为身份生命周期中的可选触发记录，而不是所有身份的必备实体；已有映射应直接表现为已授权或已停用，不补造待处理历史。

[需要改] §6.1 授权门缺少生产启用配置检查

原文：「无角色 → 幂等登记待处理 → 显示真实状态、负责岗位、有效联系方式和下一步」

问题：§4.1 和 V1 明确责任岗位/联系方式缺失时不能生成无人承接申请，但主流程没有这个分支。实现者可能照主流程先建申请，再发现没有联系人，重新制造“有状态、无人处理”的死路。

建议：在登记待处理前增加生产启用配置判断；未就绪时只显示“尚未完成启用配置”和运维恢复指引，不建立可运营申请，配置就绪后用户重新认证再进入正常待处理闭环。

[冲突] §6.3 把“凭据恢复成功”和“安全通知闭环”画成单一结束链

位置 A：「原子更新凭据……并写通知 outbox → 通知异步投递」（架构师）

位置 B：「外部通知失败时不得回滚已经原子完成的安全恢复」（架构师 §3.3）

问题：数据库恢复已成功后，外部投递可能仍待处理或失败。当前流程没有区分“Admin 凭据已恢复”和“恢复安全处置已闭环”，用户和运维可能把前者误看成通知也已完成。

建议：明确两个可观察状态：`凭据恢复完成，通知待处理/失败待补偿` 与 `恢复安全处置已闭环`。前者允许 Admin 使用新凭据登录，但必须持续告警且不能显示“通知成功”；后者只有投递成功或认可补偿证据齐备时成立。

[需要改] §6.3 保存型恢复码流程缺少新恢复码结果

原文：「消费恢复码、递增凭据代次、撤销旧 Admin 会话并写审计」

问题：V1 和 AC-F09-05 要求重新绑定 TOTP 后使旧恢复码集合失效，并生成仅当次展示的新恢复码。架构流程遗漏新码生成与保存确认，Admin 可能恢复登录后立刻失去下一次自助恢复能力。

建议：在保存型恢复路径补充“生成新恢复码 → 当次展示并确认保存 → 新 TOTP/新恢复码生效、旧材料和旧会话失效”的完整结果，并与工程稿保持一致。

[需要改] §6.4 未定义既有有效映射首次进入 F09 后的状态

原文：「`[*] --> 待处理: 无唯一有效业务角色的钉钉身份首次认证`」

问题：状态机只覆盖无角色身份。部署 F09 前已有有效映射的用户，其统一身份详情应该直接显示“已授权”，而不能要求先变成待处理或等一次新的角色操作。

建议：增加“既有唯一有效映射 → 已授权”的初始化/投影入口，以及“既有停用映射 → 已停用”的入口；明确这只是反映当前事实，不新增审批历史或重新授权。

[建议] §3.1、§6.1 补充旧 AC-F07-06 的兼容关系

建议：明确 F09 只替换 AC-F07-06 中“钉钉认证成功但无有效唯一角色”的用户结果为 AC-F09-07/08 待处理闭环；钉钉认证失败、登录态失效仍沿用既有失败语义，F07 其他权限行为不变。这样 Controller 合并时不会留下“通用联系运维”和“产品内待处理”两个冲突事实源。

[建议] §4.1 度量事件避免把“审批材料可用时间”写成系统已验证外部进度

原文：「审批完成时间，由审批证据确认」

问题：产品在 Admin 提交前不知道外部审批进度。若字段命名成系统事实，可能和“不持久化已审批待配置”冲突。

建议：统一为“Admin 提交的审批时间”和“审批材料进入本次配置的时间”，并标明前者来自外部证据、不是产品自动感知的审批状态。

## PM 评 工程师章节

[需要改] §5 FR-9.5 缺少已有授权身份的发现入口

原文：「位置：Admin 待处理列表、统一身份详情，以及新增/变更/停用/恢复的独立高风险确认表单」

问题：待处理列表只能找到无角色身份。Admin 要变更、停用或恢复一个既有运营/运营主管时，没有明确的已授权/已停用身份列表或检索入口；“统一身份详情”存在但用户无法到达。

建议：在首发管理导航中明确一个非组织目录化的身份列表/检索入口，至少支持按当前状态和可核验身份信息找到既有已授权、已停用身份并进入统一详情。保持单人操作、两个固定角色，不增加批量能力。

[冲突] §5 FR-9.3 的“完成恢复”按钮与异步通知语义不一致

位置 A：「完成恢复……禁用条件：通知/补偿条件不成立」（界面表）

位置 B：「外部通知异步投递……投递失败不回滚已安全完成的数据库恢复」（交互逻辑）

问题：主通道提交时可用但随后投递失败时，凭据已经恢复，不可能再通过禁用按钮阻止。若把外部投递列为恢复完成前置，就重新伪造跨系统原子；若完全不阻止，又可能让用户误以为安全处置已闭环。

建议：把页面结果拆为“凭据恢复完成”和“通知/补偿处置状态”。提交前只校验通知任务可持久化或已选择认可补偿路径；外部投递失败后显示持续待处理/告警，不能写“旧凭据状态不变”。

[冲突] §10 AC-F09-06 的失败回滚范围过大

位置 A：「任一步失败时旧凭据状态不变」（工程师 AC-F09-06）

位置 B：「投递失败不回滚已安全完成的数据库恢复」（工程师 FR-9.3）

位置 C：「任一步失败均不得留下部分新凭据」（PM AC-F09-06）

问题：“任一步”会把异步通知投递也纳入凭据事务，三处会产生两种实现。

建议：统一为：新凭据、旧会话撤销、恢复口令消费、管理审计和通知任务入队任一失败时，凭据事务整体不成功；通知任务已经持久化后的外部投递失败不恢复旧凭据，而进入可追踪告警/补偿状态。PM R3 也应同步修正 AC-F09-06。

[冲突] §10 对 AC-F09-09/10 的语义分配与 PM 稿不同

位置 A：工程师把 AC-F09-09 定义为“展示并核验两个权威属性”，AC-F09-10 定义为“审批完整后新增授权成功”。

位置 B：PM 把 AC-F09-09 定义为“核验完整后新增授权成功”，AC-F09-10 定义为“身份或审批不足时拒绝”。

问题：同一稳定 AC ID 出现两套含义，后续 requirements 和验收无法唯一追溯。

建议：R3 统一采用更易拆分的口径：AC-F09-09 承载身份核验不足时禁止提交；AC-F09-10 承载身份与审批均完整时新增唯一角色成功。审批字段缺失/证据不认可的拒绝结果并入 AC-F09-09 或 AC-F09-10 的异常条件，但两稿必须逐字对齐，不新增 AC。

[需要改] §5 FR-9.1 对初始化失败后已展示恢复码的处理不明确

原文：「TOTP 通过后仅当次展示；确认保存后……提交」「任一失败都不得显示创建成功」

问题：用户可能已经保存了一组恢复码，但最终创建事务失败；如果页面只回到可继续步骤，用户无法判断已保存代码是否有效，日后会拿无效码恢复。

建议：明确事务未成功时此前展示的恢复码全部无效，页面必须提示丢弃；重新开始时生成全新恢复码。事务成功但响应丢失时不得重新展示或生成，应引导正式登录并通过后续安全设置重新生成。

[需要改] §5 FR-9.5 使用“审批时间明显晚于提交时间”这一含糊条件

原文：「审批时间……格式非法或明显晚于提交时间」

问题：“明显晚于”没有唯一含义，可能导致同一证据在不同实现中被接受或拒绝；PM 验收也无法写出唯一可观察结果。

建议：不要使用“明显”。若产品要阻止未来审批时间，应写成可比较的明确规则并统一时区口径；若该规则尚未获得治理确认，则只校验可解析和必填，把异常未来时间标为需人工核验，不擅自发明容差。

[冲突] §7.5 新增了未确认的浏览器与移动端范围

位置 A：「PC Chrome 普通浏览器：真实首发验收表面」「移动端可显示安全退出或转 PC 指引」（工程师）

位置 B：「PRD V0 未确认浏览器、移动端……V0 不新增兼容承诺」（现有 F01—F08 §7.5）

问题：F09 V1 只确认继承既有 PC 设计体系，没有拍板浏览器版本矩阵或新增移动端页面。工程稿既把 Chrome 提升为承诺，又新增移动端指引，扩大了首发范围，并可能造成 F09 比既有业务页面更窄或更宽的兼容口径。

建议：删除具体浏览器承诺和移动端新增表面；写成“继承现有产品已支持的 PC 浏览器范围，身份隔离与秘密保护不得因浏览器不同而降级”。若设计阶段需要具体矩阵，再由有权角色确认。

[需要改] §5 FR-9.4 与既有 AC-F07-06 的无角色结果需要显式替换关系

原文：「无角色身份进入待处理状态页」

问题：现有 AC-F07-06 仍写“未配置有效角色时拒绝并提供联系运维/系统管理员指引”。若不注明影响面，最终 PRD 会同时保留通用错误恢复和 F09 待处理状态两个结果。

建议：在 FR-9.4 明确：F09 生效后，AC-F07-06 的“认证失败/登录态失效”分支保持不变；仅“认证成功但无唯一有效角色”分支由 AC-F09-07/08 细化为幂等待处理和责任承接。

[需要改] §5 FR-9.4 缺少已配置用户在旧页面中的即时反馈

原文：「配置后提示退出并重新钉钉登录」「角色已配置但使用旧会话：提示重新登录」

问题：用户在待处理页打开期间，Admin 可能已配置角色。若页面只依赖再次 OAuth 才更新，用户仍会误以为无人处理；若自动把旧页面变成业务会话，又违反会话隔离。

建议：允许待处理页刷新或重新查询后显示“已配置待重新登录”，但绝不在原页面热升级为业务会话；唯一主动作仍是重新发起钉钉登录。

[建议] §5 中 `FR-9.1—FR-9.7` 应明确只是 F09 子章节标签

问题：共享注册表没有 `FR-9.1—FR-9.7` 稳定 ID，只有 F09、US/REQ/AC/NFR。当前写法容易被下游当成另一套可追溯 ID。

建议：标题改为“F09.1—F09.7 功能小节”或在 §5.1 明确 FR 标签仅为最终 PRD 阅读序号、不是稳定需求 ID；所有机器追溯仍只使用注册表 ID。

[建议] §5 FR-9.7 删除“统计大屏/价值分析”作为不存在的界面元素

原文：「统计大屏/价值分析｜不提供｜不存在」

问题：把明确不做的能力列入界面元素表，可能被误读为需要实现一个禁用占位或空入口。

建议：保留在明确边界和范围停止线即可，不作为页面元素。

[需要改] §7.6 的 F01—F08 不变行为需扩展到认证成功后的入口兼容

原文：「F09 故障不得改变 F01—F08 固定规则、经营数据、行动任务、业务审计或既有双角色权限语义。」

问题：这句话保护了业务数据和权限，却未保护已有有效运营/主管用户的正常登录路径。F09 增量若错误地要求所有人先进入待处理，会让既有用户回归失败。

建议：追加：已有唯一有效角色的钉钉用户继续按既有路径建立业务会话并进入对应工作台，不经过待处理或 Admin 再审批；F09 管理面不可阻塞其正常登录。

## R2 结论

- 两稿总体遵守单 Admin、双业务角色、审批/执行分离、管理/业务权限正交和非通用 IAM 边界，没有要求新增功能 ID。
- R3 必须优先解决三项 P0：已有授权身份的发现/管理闭环、部署恢复成功与通知闭环的双状态、AC-F09-09/10 唯一语义。
- 其次统一旧 AC-F07-06 的影响范围和 F01—F08 已授权用户不变行为，避免 F09 上线后让现有用户误入待处理。
- 浏览器、移动端、审计期限和具体安全参数均不得在未拍板前形成新增产品承诺。
