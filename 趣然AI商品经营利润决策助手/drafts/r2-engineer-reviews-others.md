# r2-engineer-reviews-others.md · 工程师评审 PM 与架构师 R1

## 评审结论

| 级别 | 数量 | 结论 |
|---|---:|---|
| P0 | 0 | 未发现会让需求集合必然不可同时满足或直接导致数据安全错误的冲突 |
| P1 | 13 | 会造成 AC 语义分叉、重复批次、状态覆盖、AI 阻塞或权限/追溯实现不完整，需在 R3 修订 |
| OPEN_QUESTION | 1 | 业务时区未在用户确认基线中出现，需要 Controller 或有权业务方确认 |
| 建议 | 3 | 不阻塞 MVP，但修订后可减少后续设计歧义 |

> 本轮不修改 R1 原稿。PM 对 §10 的 AC 正文拥有主笔权；工程师稿中与 PM 最终 AC 语义不一致的清晰度复核表，应在 R3 按最终注册表与 PM 修订稿同步。

## 对 PM R1 的评审

### PM-P1-01 · 行级异常与批次级异常被合并为一个 AC

[需要改][P1] §10.2 AC-4（AC-F01-04）

原文：「当上架日期、必需数值或数据期间不可解析时，该明细应显示字段级异常，且不生成依赖该异常字段的经营动作。」

问题：上架日期/必需数值是 SPU 行级异常，数据期间是批次级口径；三者的产品结果不同。上架日期异常会让该 SPU 不分类，利润缺失只阻断利润相关动作，而数据期间非法应阻断批次相关指标或整批生成。当前一句同时包含多个触发条件和多个结果，不满足“一个 AC 一个唯一可观察结果”，实现方会分叉为“排除整行”“只阻断部分动作”或“阻断整批”。

建议：把批次期间有效性与行级字段异常拆开。若现有 AC 数量不足，由 Controller 在 `id-registry.md` 末尾追加新 AC ID，不复用或改写已登记 ID；行级 AC 明确每类字段的降级范围，批次级 AC 明确是否禁止生成清单。

### PM-P1-02 · 批次幂等和重复清单没有对应 AC

[需要改][P1] §10.1 AC-F01-01～AC-F01-02、§10.3 AC-F05-02

原文：「当运营选择玩具事业部并导入一份包含 10—20 个有效真实 SPU 的经营表时，系统应接受明细并显示本次导入批次。」

问题：F01/F05 的工程边界要求同一事业部、同一期间、相同文件内容重复提交时返回既有批次，且同一批次只能有一份清单。PM 的 AC 只覆盖首次导入和历史清单保留，没有覆盖重复提交的唯一结果。缺少该 AC 会让实现允许同一周生成多份建议与执行链，直接破坏 NFR-005 追溯和轻闭环。

建议：在 REQ-F01-01/REQ-F05-01 下增加独立 AC：相同事业部、期间和文件内容再次提交时返回既有批次/清单，不新增建议、不覆盖状态。新增 ID 必须由 Controller 统一追加到注册表。

### PM-P1-03 · 分类和动作 AC 未写明数值边界

[需要改][P1] §10.1 AC-F03-01、AC-F03-03

原文：「当上架日期与上一个完整自然月净销售额均可用时，系统应为该 SPU 显示新品、大爆款、小爆款或淘汰商品中的唯一分类。」

原文：「当 SPU 的分类、经营准利润率和已校验品退率满足固定规则时，系统应显示清仓、止损、观察、加投或维持中的唯一主动作。」

问题：“满足固定规则”没有在 AC 中明确引用哪张规则表，也没有覆盖等号边界。`100,000/20,000`、`0%/5%/10%/15%/-20%`、`1.5%` 与新品满 2 个自然月均会造成实现分支；例如品退率恰为 1.5% 不观察，利润率恰为 -20% 的新品应加投。

建议：AC 明确引用 §3 的版本化规则表，并在正文列出关键等号归属；至少覆盖新品恰满 2 个月、销售额恰为 20,000/100,000、品退率恰为 1.5%、利润率恰为各类型边界的唯一结论。

### PM-P1-04 · 并发审核与重复提交没有可观察 AC

[需要改][P1] §10.3 AC-F06-05～AC-F06-06

原文：「当执行人提交执行结果时，系统应在该建议下显示执行时间、执行备注和结果状态。」

问题：现有 F06 AC 全部用于正常状态推进，没有覆盖两名主管同时审核、过期页面提交、网络重试导致重复执行事件等冲突。FR-6 与 NFR-005 已要求不能后写覆盖；没有产品可观察 AC，设计和实现可能选择静默覆盖。

建议：为 REQ-F06-03 增加并发冲突 AC：两个操作者基于同一旧状态提交时，仅首个合法变更成功，后续提交显示冲突和最新状态，且不新增重复事件。不要把它与正常结果记录合并为一个 AC。

### PM-P1-05 · 双动作执行与“当前唯一状态”冲突，结果记录责任也不清

[冲突][P1] §2.4 US-F06-02、§10.3 AC-F06-03～AC-F06-06 跟架构稿 §4.2、§6.3 及工程稿 FR-6 不一致

位置 A：「作为运营或采购计划，我希望按职责更新执行时间、执行备注和结果状态。」

位置 B：「当建议沿‘待审核→已通过→待执行→已执行→已记录结果’推进时，系统应显示当前唯一状态。」

位置 C：「一个 DECISION_RECORD 可拆为最多两个 ACTION_ITEM……分别分派、分别追踪。」

问题：加投可与补货并存，因此同一建议可能有运营和采购两个独立执行状态，不存在始终唯一的执行状态。用户已确认运营负责销售额、利润和库存结果，采购计划负责补货执行；US-F06-02 中“结果状态”会被理解为采购也能记录经营结果。

建议：统一为“建议级审核状态 + 动作项级执行状态 + 建议级经营结果记录”。运营主管一次审核建议；运营和采购分别更新自己的动作项；仅运营记录经营结果。PM 的 US/AC 应明确双动作部分完成时的可观察状态，不能用一个“已执行”覆盖另一动作尚未执行。

### PM-P1-06 · NFR-003 凭据保密没有对应产品结果

[需要改][P1] §10.2 AC-F04-04、§10.4 权限兼容

原文：「当 LiteLLM 不可用时，系统应继续显示固定规则结论与结构化依据，并将 AI 解释显示为生成失败。」

问题：该 AC 只覆盖 NFR-004 的 AI 降级，没有覆盖 NFR-003：普通用户不可查看 deployment secret，且首版不得存在管理员后台或用户自助配置入口。架构稿虽写明配置责任，但 §10 没有唯一可观察结果，后续可能误建配置页或在错误响应中暴露凭据。

建议：增加独立 AC 或在有效 REQ 下追加稳定 AC ID：普通用户访问产品页面、接口和 AI 错误详情时，不存在密钥配置入口且响应不返回 deployment secret；运维配置不通过普通用户页面完成。

### PM-P1-07 · 未登记的 legacy AC ID 会破坏稳定 ID 单一来源

[需要改][P1] §10 各 AC 标题

原文：「括号前的 legacy ID 用于兼容既有检查。」以及「AC-1（AC-F01-01，关联 REQ-F01-01）」

问题：`id-registry.md` 只登记 `AC-Fxx-xx`，没有登记 `AC-1`～`AC-39`，也没有任何“既有检查”证据。额外 legacy ID 形成第二套编号，合并和生成 `requirements.md` 时可能被误当作正式 AC，违反“唯一 ID 来源、发布后不重排复用”。

建议：正式 PRD 只保留注册表中的 `AC-Fxx-xx`。如确有兼容系统，需先由 Controller 把映射作为结构化注册表登记；在此之前删除未登记 legacy ID 与“兼容既有检查”的无依据表述。

### PM-P1-08 · 溯源 AC 未要求规则版本

[需要改][P1] §10.4 AC-F08-01

原文：「系统应显示其导入批次、数据期间、触发规则、原始关键值和生成时间。」

问题：只记录“触发规则”但不记录 `rule_version`，规则阈值调整后无法确认历史建议使用的是哪一版规则，NFR-001 的确定性与 NFR-005 的历史重放会失去关键输入。架构和工程稿均把规则版本作为批次/建议追溯必需项。

建议：在唯一可观察结果中加入“规则版本”，并保持历史页面使用生成时固化的版本，不以当前规则覆盖。

### PM-S-01 · 首批固定日期与通用期间行为可再分层

[建议] §10.1 AC-F01-02

建议：保留首批 `2026-06-01—2026-06-30` 的验收事实，同时补一句通用不变行为：后续批次展示显式声明的上一个完整自然月起止日，不从“上一周”等自然语言表头推断。这样不会把产品实现写死为仅能处理 2026 年 6 月。

## 对架构师 R1 的评审

### ARCH-P1-01 · 重复文件仍允许“确认创建新批次”，与幂等约束冲突

[冲突][P1] §4.4 导入幂等建议跟工程稿 FR-1、§7.1 不一致

位置 A：「以事业部、数据期间和源文件内容摘要组合识别疑似重复导入，并要求操作者确认是否创建新批次。」

位置 B：「相同内容重复导入返回原批次，不重复计算、不新增建议。」

问题：相同事业部、期间和文件内容不是“疑似”重复，而是同一业务输入；允许用户确认后创建新批次会产生两份清单和两条状态链，与“同一批数据只生成一份行动清单”冲突。

建议：相同三元组直接返回既有批次，不提供创建新批次选项。只有同一事业部/期间但文件内容不同才允许建立独立更正批次，并显式关联原批次且不覆盖历史。

### ARCH-P1-02 · 核心流程把审核放在 AI 完成之后，可能阻塞轻闭环

[冲突][P1] §6.1、§6.4 跟 §3.6、NFR-004 不一致

位置 A：「生成本批次唯一行动清单 → 异步请求 LiteLLM → 成功/失败 → 运营主管审核。」

位置 B：「若解释层失败，行动清单仍……显示结构化依据及‘AI 解释生成失败’。」

问题：流程图和时序图均把审核节点放到 LiteLLM 返回成功或失败之后。如果网关长时间无响应且尚未返回失败，主管无法进入审核；这与“AI 失败不阻断清单、审核和执行”不一致。

建议：清单就绪时立即具备结构化兜底并可审核；AI 解释作为并行、可追加的独立状态。流程图从“清单就绪”直接连接审核，同时另开 AI 成功/失败分支更新解释，不把 AI 响应作为审核前置条件。

### ARCH-P1-03 · 建议级审核与动作项级执行的状态归属没有定清

[需要改][P1] §4.2、§4.3、§6.3

原文：「一个 DECISION_RECORD 可拆为最多两个 ACTION_ITEM……ActionItem.workflow_state：待审核、已通过、已驳回、待执行、已执行、已记录结果。」

问题：如果每个动作项都有完整审核状态，主管可能只通过加投而未通过补货；如果两个动作共享审核，Schema 又没有建议级审核实体。并且两个动作独立执行时，`已记录结果` 属于哪个 ActionItem 不明确。PM 要求建议级唯一状态，工程稿要求双动作分别执行，三者无法直接合并。

建议：明确状态分层：`DecisionRecord/Recommendation` 保存一次建议级审核结果；`ActionItem` 只保存各自动作执行状态；经营结果记录绑定建议或决策，由运营提交。若坚持动作项分别审核，必须在产品行为中明确主管能否分别通过/驳回，但该能力当前未获用户确认，不宜新增。

### ARCH-P1-04 · 数据模型与时序缺少并发版本约束

[需要改][P1] §4.3 Schema、§6.3 行动状态机

原文：「ActionEvent……追加写入，不修改旧事件。」

问题：追加事件只能保留历史，不能阻止两个基于同一旧状态的审核/执行请求都成功。Schema 没有状态版本或等价并发前置条件，状态机也没有“版本过期/冲突”分支；会发生后写覆盖或重复执行事件。

建议：在建议级审核和动作项级执行记录中增加可比较的状态版本/前置状态标识；每次迁移只接受当前版本，冲突请求不改变状态并返回最新状态与操作者。具体数据库或锁实现保持技术中立。

### ARCH-P1-05 · 经营结果只有备注字段，无法承载已确认的结果责任

[需要改][P1] §4.3 ActionEvent、§6.3

原文：「ActionEvent.actor_ref/occurred_at/note：内部账号、时间点、备注。」

问题：用户已确认运营负责动作执行后的销售额、利润和库存结果；当前模型只有通用 `note` 和状态，无法区分结果状态、结果周期、销售额/利润/库存值是否提供，也无法稳定追溯 PM 的“已记录结果”。把所有内容塞进备注会造成不可计算、不可复核。

建议：在不指定物理 Schema 的前提下，补充结果记录的逻辑字段：结果状态、结果记录人、结果时间、结果观察期间，以及可选的销售额/利润/库存结果值或“未提供”状态；由运营提交，并与原始规则输入分离保存。

### ARCH-OPEN-01 · `Asia/Shanghai` 是未确认的产品行为假设

[OPEN_QUESTION] §3.2、§4.3、§4.5、§9.A 业务日期与时区

我的判断：自然月、新品满 2 个月、7 日/14 日窗口必须有统一业务时区；对当前中国内部业务，`Asia/Shanghai` 是合理推荐。

你的判断：「按 Asia/Shanghai 的业务日期冻结」「自然月、7 日窗口、14 日窗口……均按 Asia/Shanghai 解释。」

需要 Controller 或企业家裁决：用户确认基线没有明确时区，`assumptions.md` 又声明当前无未确认假设。应由有权方确认后写成产品约束；确认前只能标“架构建议：Asia/Shanghai”，不能当作已确认事实。

### ARCH-S-01 · “维持/不补货”是否生成可执行动作项需要明确

[建议] §4.2、§4.3 ActionItem

建议：明确仅可执行动作进入 `ActionItem`。主动作“维持”且无补货建议时只保留 `DecisionRecord`，默认不进清单；数据完整得出的“不补货”是可见结论还是需采购确认的任务，应与 PRD V0 的“采购查看补货/禁止补货”边界一致，避免生成无法执行的待办。

### ARCH-S-02 · 更正批次需要显式关联原批次

[建议] §4.3 ImportBatch、§4.4

建议：既然架构稿允许“新/修正批次”，逻辑模型应保留可选的原批次关联和更正原因，使用户能区分每周新数据与同期间数据修正；该字段只服务追溯，不得允许覆盖原批次。

## 跨作者一致性要求

1. PM 是 AC 正文主笔，R3 应先确定现代 AC ID 的最终语义；工程师的 §10 清晰度复核必须按该语义同步，不能保留另一套 AC 含义。
2. 架构师和工程师统一“清单就绪即可审核、AI 独立追加解释”的流程，LiteLLM 任何等待或失败都不得阻断固定规则轻闭环。
3. 三方统一状态分层：建议级审核、动作项级执行、建议级经营结果；加投+补货时允许部分执行，但不能把部分执行显示为整条建议完成。
4. 三方统一批次身份：事业部+数据期间+文件内容相同即幂等返回；同期间内容不同才是新/更正批次，历史不可覆盖。
5. 三方统一数据权限：采购计划仅获得补货/禁补、SPU 身份、库存和销量必要依据；规则、接口、筛选、导出和审计均按同一字段投影。
6. 三方统一追溯字段：批次、期间、SPU、规则版本、触发规则、原始关键值、生成时间、状态前后值、操作者和备注不可被新批次或状态更新覆盖。
