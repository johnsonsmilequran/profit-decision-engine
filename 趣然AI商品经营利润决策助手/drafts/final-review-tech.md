## P1

### P1-1：需求契约仍把“库存可售天数”命名为“库存周转天数”

- 证据：`output/requirements.md` §F02 的 REQ-F02-03（第 120—126 行）使用“库存周转天数”；`output/PRD详细版.md` §3.2、§3.5 和 `output/PRD-dev.md` §5.1（第 54 行）均定义为 `(仓内库存+在途库存)/最近 14 天平均日销量` 的“库存可售天数”。
- 影响：`requirements.md` 被声明为最高实现权威，错误术语可能让实现、字段命名或报表解释落成历史库存周转指标，而不是未来可售天数。
- 最小修复：保留稳定 ID `REQ-F02-03`，仅把标题和 Behavior 中的“库存周转天数”统一改为“库存可售天数”；AC-F02-05/06 无需改 ID。

### P1-2：必要身份字段的行拒绝条件在正式 PRD 与需求契约中不一致

- 证据：`output/PRD详细版.md` §3.2（第 186—195 行）规定 SPU ID、链接名称、店铺、平台、责任运营任一缺失都拒绝该行；`output/requirements.md` AC-F01-04（第 83—92 行）只明确 SPU ID 缺失或重复时拒绝，未说明其余四项。
- 影响：按最高权威契约实现时，链接名称、店铺、平台或责任运营缺失的行可能继续进入规则，产生无法展示、无法隔离事业部或无法分派的建议。
- 最小修复：在 AC-F01-04 中显式列出五个必要身份字段，并写明“任一缺失或 SPU ID 批次内重复则拒绝该行”；保持指标字段级降级规则不变。

### P1-3：动作项在规则事务中“创建”还是在审核通过时“生成”存在双重语义

- 证据：`output/PRD详细版.md` §4.2、§4.4（第 353—355、431—439 行）规定动作项随固定规则决策原子生成，审核通过时只激活；`output/requirements.md` REQ-F06-01（第 479—485 行）也写“激活动作”，但 AC-F06-01（第 503—512 行）写成审核通过后“生成……待执行任务”。
- 影响：若实现按 AC 在审核事务中再次创建任务，可能重复生成 ActionItem，破坏止损/清仓与禁补的原子性、批次重放和一建议最多两个动作项的不变量。
- 最小修复：把 AC-F06-01 改为“激活建议内已随固定规则决策原子创建的动作项，并分别进入运营与采购计划待执行状态”；驳回仍只关闭既有动作项。

## P2

### P2-1：AI 降级 NFR 的 Applies-to 未包含直接承载失败行为的 REQ-F04-03

- 证据：`output/requirements.md` NFR-004（第 732—737 行）只关联 REQ-F04-01、REQ-F04-02；AI 失败不阻塞与凭据行为实际定义在 REQ-F04-03（第 320—326 行附近）。
- 最小修复：将 `REQ-F04-03` 加入 NFR-004 的 Applies-to；现有 AC-F04-04 已能验证该行为。

### P2-2：逻辑模型缺少对决策和动作去重键的显式约束

- 证据：`output/PRD详细版.md` §4.2 用 ER 关系表达一个快照对应一个决策，并规定一条建议最多一个经营动作和一个库存动作，但 §4.3 只显式声明批次指纹、`batch_id + spu_id` 和 `decision_id` 唯一，未显式声明决策/动作的业务唯一键。
- 风险：规则处理崩溃重试或并发恢复时，若实现者只落实当前列出的唯一约束，仍可能创建重复 DecisionRecord 或同类型 ActionItem。
- 最小修复：在 Schema 草案补充逻辑唯一约束：`DecisionRecord(batch_id, spu_id)` 唯一，`ActionItem(decision_id, action_type)` 唯一；物理索引形式留给设计阶段。

### P2-3：身份接入是权限实现前置能力，但未进入需求契约的能力前置表

- 证据：`output/PRD详细版.md` §9.C 指出三角色身份能力的接入方案未确认且不可用时不得使用共享账号；`output/PRD-dev.md` §11、§13（第 173、196 行）也把身份接入列为 F07 前置并标注待确认；`output/requirements.md` 的 Capability prerequisites 目前只有周度表格和 LiteLLM。
- 风险：F07 被标为 active，但实施排期可能在没有可识别角色与操作者的情况下误以为已具备前置条件，最终只能做前端隐藏或共享账号，违背 NFR-002/NFR-005。
- 最小修复：在开发启动清单或能力前置表增加“可认证并映射运营/运营主管/采购计划的身份能力”，状态明确为待设计确认；在能力就绪前不得开放真实数据写操作。不要虚构具体 SSO、负责人承诺或截止日。

## 已确认无阻塞的问题

- 固定规则阈值、等号边界和优先级在三份文件中一致，AI 不参与分类或动作裁决。
- 止损/清仓与禁补被定义为同一规则决策事务的原子结果；加投与补货可并存。
- 批次指纹命中返回原批次，历史规则和状态不被当前规则覆盖。
- 审核使用建议级 version，经营与采购动作分别使用动作级 version；过期提交不覆盖成功状态。
- LiteLLM 解释在清单发布之后异步追加，失败、超时或越界不阻塞审核执行；部署密钥归运维且普通用户不可见。
- Python/FastAPI、React、PostgreSQL 与容器化均明确标注为待设计确认的可替换建议，没有越权写成已拍板技术决策。
