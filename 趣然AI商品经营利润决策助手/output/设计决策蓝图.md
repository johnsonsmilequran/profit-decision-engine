# 设计决策蓝图

> 状态：用户已确认推荐骨架，并授权 AI 按 PRD 自主收敛其余决策、不再提问。需求契约：revision 2，workflow_mode: standard。

## 1 盘子

- 端形态 / 响应式：阶段 1 仅建设内部 PC Web 工作台，最小适配宽度 1024px，主设计宽度 1440px；不建设移动端、平板专版或小程序。
- 工作台聚合（DEC-001）：登录后按当前角色聚合最新批次状态、清仓/止损等风险概览、待审核/待执行/待记录结果、双动作进度不一致的跨部门卡点。
- 核心目标：让玩具事业部每周导入 SPU 经营表后，以固定规则形成唯一行动清单，运营主管整体审核，运营与采购计划分动作执行并留痕；AI 只解释、不改规则。

## 2 信息架构与站点地图

- 导航模式（DEC-002）：固定左侧栏 + 页面面包屑；一级入口为工作台、数据批次、行动清单、历史追溯。
- 页面调用骨架：钉钉认证门禁 → 角色工作台；工作台 → 最新批次详情 / 已带角色筛选的行动清单；数据批次列表 → 新建导入 → 批次详情 → 对应行动清单；行动清单 → 建议详情 → 审核或责任动作表单 → 返回详情；历史追溯 → 历史批次详情或历史建议详情。
- 404/500 不独立建设业务页；路由不存在与服务失败统一使用应用壳内错误状态，避免伪造无需求来源的公共站点。

## 3 角色与权限

- 上游认证方式：钉钉是唯一统一身份入口；每人独立登录。角色变更由事业部负责人审批，IT/运维在系统侧配置；产品不提供账号密码、注册、找回密码或角色管理后台。
- 登录恢复：认证失败或登录态失效时返回认证门禁并可重新发起钉钉认证；无有效角色显示“未配置业务角色，请联系 IT”，不得默认赋予运营角色。
- 同页角色差异（DEC-003）：服务端先裁剪数据，界面隐藏无权操作；越权直达显示权限不足且不返回业务对象身份和状态。运营、运营主管可见完整经营信息，采购计划仅见补货/禁补及库存销量必要依据。

## 4 页面地图与设计深度

- F01 数据导入与校验：批次列表 → 新建导入 → 批次详情/校验结果三页。每页均明确空、加载、网络错误、权限不足；详情另有处理中、导入失败、部分成功、指纹命中原批次。
- F02 指标计算：不新建重复业务对象；指标结果进入批次详情和建议详情，使用“原始值 / 采用值 / 周期 / 状态 / 降级原因”五列结构，异常不伪造默认值。
- F03 固定规则决策：规则结果进入建议详情，突出唯一商品类型、唯一主动作、补货/禁补组合、规则版本与触发链；止损/清仓与禁补原子同显。
- F04 AI 解释：与规则结论同页但视觉降级；结构化四要素始终先显示，AI 独立显示待生成/生成中/成功/失败/越界舍弃，不提供用户重试或密钥入口。
- F05 行动清单：独立列表页 + 建议详情页。列表服务端分页，默认每页 20 条，支持动作、店铺、责任运营、审核状态、执行状态筛选；不做无限滚动、批量操作或导出。
- F06 审核与执行：建议详情内按权限出现审核、经营动作、采购动作入口；复杂提交各使用独立全屏抽屉式表单页面，结果提交成功后返回建议详情。version 冲突保留表单草稿并要求刷新确认，不覆盖现状。
- F07 权限隔离：认证门禁页 + 全站服务端字段裁剪 + 应用壳内权限不足状态；不建设角色管理页。
- F08 规则与数据溯源：批次详情和建议详情的“依据与溯源 / 状态时间线”承载；历史入口复用批次列表与行动清单的批次切换，不创建第二套历史实体。
- 后续 planned：评价主题、退款/退货原因、广告计划/关键词/素材、自动写入广告/采购/库存系统、SKU 级能力。依赖相应明细数据、责任人和新阶段需求契约后重新深设计。
- 后续不可逆约束（DEC-004）：MVP 保持不可变 `batch_id`、稳定 `spu_id`、建议与动作分层 ID、追加事件模型、规则版本快照、角色裁剪接口；未来明细与自动写入只能挂接这些稳定主体，不改变历史快照。

## 5 通用交互范式

- 列表（DEC-005）：服务端分页 + 显式搜索/筛选/排序；筛选条件写入 URL，刷新可恢复。首版无批量审核、批量执行、导出和无限滚动。
- 表单：字段失焦校验，提交时全量校验；必填项显式标记。新建导入页不自动保存包含文件的草稿，离开时仅在已选文件或已填写字段后拦截；审核/执行表单在本地会话保留未提交文本，version 冲突不自动重放。
- 反馈：轻量成功使用 Toast；不可逆状态提交（通过、驳回、确认执行）使用摘要确认；权限、网络、并发冲突使用页内提示，不能以 Toast 代替可恢复路径。
- 危险操作：V0 没有删除；审核和执行事件不可撤销覆盖，只能保留历史并由后续新事件表达更正。

## 6 视觉风格锚点

- 明暗 / 风格：浅色、Professional & Corporate 与现代零售运营仪表感；拒绝科幻 HUD 和消费端促销感。
- Category：E-Commerce & Retail。
- 情绪：冷静、清楚、可信、可行动；风险应醒目但不制造恐慌。
- 交互哲学（DEC-006）：色彩响应型。hover 只改变边框/背景色，active 加深色阶，禁止阴影抬升与物理位移混搭。
- 字体：中文正文使用系统无衬线，数据使用等宽数字栈；高密度表格保持清晰对齐。
- 设计签名：每条关键建议都有一条“利润—库存双轨决策带”，左轨呈现经营主动作，右轨呈现补货/禁补，两轨由同一规则节点连接，直观暴露跨部门卡点。
- 色彩方向：暖白纸张背景、墨黑文字、克制靛蓝品牌色；清仓/止损使用不同层级的红橙语义，观察为琥珀，加投为靛蓝，补货为青绿。

## 7 数据与集成

- 核心实体：UserIdentity、RoleMapping、ImportBatch、SPUSnapshot、FieldQuality、MetricSnapshot、RuleVersion、DecisionRecord、ActionItem、AIExplanation、AuditEvent、OutcomeRecord。
- 外部对接：数据支持部门周度 XLSX、钉钉统一身份、既有 LiteLLM 网关。V0 不接广告、采购、库存数据库，不自动写外部系统。
- 接入方式：XLSX 经产品后端上传解析；钉钉和 LiteLLM 均经服务端 API；禁止浏览器直连数据库或携带 deployment secret。
- 同步策略：数据每周一人工导入形成不可变批次；角色每次请求按钉钉映射/服务端会话校验；AI 在规则完成后异步调用，失败不阻塞。
- 前置能力：周度经营表 ready（数据支持部门）；LiteLLM ready（运维，连通性待实施验证）；钉钉与三角色映射 committed（事业部负责人审批、IT 配置，连通性待实施验证）。库存与可信 7 日品退缺失时按 requirements 的字段级降级继续。

## 8 技术栈、架构与部署

- 前端：React + TypeScript + Vite，单页 PC 管理端；TanStack Router、TanStack Query、React Hook Form、Zod。选择轻量应用而非 SSR 全栈框架。
- 后端：Node.js LTS + Fastify + TypeScript；固定规则模块保持纯函数，批次处理可由同进程后台任务启动，MVP 不引入外部队列。
- 数据：PostgreSQL + Drizzle ORM；不引入缓存、搜索引擎、向量库或 Agent 框架。
- 文件：单实例 MVP 使用服务器本地持久化目录保存原始 XLSX，数据库保存元数据和摘要；文件与数据库每日备份。多实例或磁盘不持久化时再升级国内对象存储。
- 部署：Docker 单体模块化应用部署到公司现有国内可达基础设施；反向代理终止 TLS。不得静默新增海外托管、付费 SaaS 或新平台账号。
- 国内可达：所有运行依赖可自托管；复用现有钉钉与 LiteLLM，不新增国外 SaaS。

## 9 安全与运维

- 认证：钉钉统一身份，服务端安全会话 Cookie；登录态失效重新认证，不新增产品二次验证。
- 授权：默认拒绝，服务端在查询、序列化、错误与审计详情四层裁剪；隐藏按钮不作为安全边界。
- 敏感信息：采购不可见利润、推广、品退和售后；LiteLLM deployment secret 不进入前端、响应或业务日志；AI 输入排除内部人员标识和原始整表。
- 备份（DEC-007）：PostgreSQL 与上传目录每日自动备份，保留 30 天；目标 RPO 24 小时、RTO 8 小时。恢复演练按月执行。
- 审计：所有成功状态变化追加 actor、时间、前后状态、备注和 version；越权拒绝、version 冲突进入安全审计。业务页仅展示按角色裁剪的时间线。
- 可观测：结构化日志、健康检查、批次处理状态、AI 降级率、权限拒绝和 version 冲突计数；不在 MVP 引入新付费监控服务。

## 10 需求覆盖承诺

- 稳定来源：requirements revision 2 的 22 个 REQ、41 个 AC、5 个 NFR 均进入页面、数据、接口、流程或测量设计；页面和设计 ID 发布后不重编号。
- MVP 暂无详细设计落点的 active ID：0（阶段 II 追溯矩阵需由校验器证明）。
- 后续候选没有 active REQ/AC/NFR，全部以 planned 骨架登记，不伪装为已承诺或已完成。

## 自主收敛结论

凭用户已确认的业务目标、推荐骨架和“不再提问、由 AI 采用推荐方案”的授权，本蓝图能够让固定规则、整体审核和分动作执行形成可用轻闭环；稳定批次、动作分层、追加事件与服务端权限边界也足以避免候选能力迫使 MVP 高成本返工。进入阶段 II。
