# 阶段 5 最终战略/范围评审

## 评审结论

- P0：0
- P1：2
- P2：2
- 已守住的边界：V0 只处理 SPU/商品链接；周一导入新数据后生成一份新清单；固定规则决定主动作，AI 不覆盖且不阻塞；评价、退款原因、广告明细、SKU 及外部系统自动写入均未进入 MVP。阶段 2—4 明确标记为未执行，未引入竞品、行业基准或 ROI 结论。

## P1

### P1-01 首轮完成定义遗漏“运营验收”的责任人与可观察结果

- 证据：`output/PRD详细版.md:14` 将 MVP 完成收敛为数据规模、问题数、四要素和轻闭环四项，未包含用户已确认的“首轮由运营验收”；`output/PRD详细版.md:1068-1086` 的成功指标也没有验收责任人/验收结论；`output/PRD-summary.md:49-58` 同样只列系统结果。已确认基线在 `output/PRD-V0.md:274-281` 要求“运营确认问题和建议可用于首轮业务评审”，项目纪要进一步明确首轮验收者为运营。
- 影响：即使导入、规则和状态都跑通，项目仍缺少有权给出“首轮可用”结论的明确终点，会使成功定义变成无责任人的自动指标。
- 最小修复：在 PRD §0 的 MVP 完成定义增加第五项“运营完成首轮验收，确认至少 3 个真实问题及其建议可用于业务评审”；在 §8 指标矩阵和摘要版成功标准各补一行“首轮验收责任人：运营”。这是项目验收口径，不必新增产品功能或 REQ/AC。

### P1-02 “观察动作”在同一正式 PRD 中同时被定义为已收敛和尚未确认

- 证据：`output/PRD详细版.md:27` 把含观察的角色责任标为“已确认并经 R3 收敛”；`output/PRD详细版.md:263` 又将观察归运营说成“当前采用的架构建议”；`output/PRD详细版.md:780` 称责任角色和执行终点未在基线中定义，保留待合稿确认；`output/PRD详细版.md:1157-1161` 再次称观察闭环尚未确认。但 `output/requirements.md:525-537` 已把运营执行“持续观察”写成稳定 P0 行为，`output/PRD-summary.md:18-20` 也将其列为运营责任。
- 影响：设计与开发无法判断“观察”是已拍板 MVP 闭环、设计假设，还是待确认范围；也会把阶段 5 的合稿裁决误表达为用户业务事实。
- 最小修复：保留已记入项目纪要的阶段 5 最小闭环裁决（观察归运营，以记录观察或有证据的优化动作及结果为终点），删除 §5 和 §9.2 中“待 Controller/尚未确认”的旧草稿文案；同时把 §0.2 的状态改为“核心角色责任已由用户确认；观察最小闭环为阶段 5 实现裁决（来源：AI）”，不再统称为用户已确认事实。

## P2

### P2-01 用否定句引入了无来源的“约 200 万价值”

- 证据：`output/PRD详细版.md:59` 和 `output/PRD详细版.md:1460` 写“不推算/不写约 200 万价值”，但已确认 PRD V0、用户对话与摘要版都没有这个金额来源。
- 影响：虽然它位于否定句中，仍会在正式 PRD 中制造一个似乎曾被讨论的无依据收益数字，违背阶段 2 未执行时的事实保护目标。
- 最小修复：两处都删除“约 200 万价值”，仅保留“不推算年度收益、ROI 或工时节省”；已确认的 515 案例数字照常保留。

### P2-02 LiteLLM 前置能力在 PRD 与需求契约中的“已存在/可访问”状态不同

- 证据：`output/PRD详细版.md:26,1117` 准确写为网关已存在、运行可用性待实施阶段验证；`output/requirements.md:22` 却把“LiteLLM 网关可访问”标记为 `ready`，其证据只能证明网关存在。
- 影响：不阻塞 MVP，因为已定义结构化兜底；但可能让设计/实施误以为连通性、作用域和部署密钥已验证。
- 最小修复：在 `requirements.md` 中把前置项名改为“LiteLLM 网关服务已存在”并保留 `ready`；在证据中明记“产品环境连通性与密钥作用域待实施验证”。这样不会虚构交付截止日，也不改变 AI 失败降级行为。

## 战略范围总结

MVP 的主战略与首轮验证方式与已确认 PRD V0 一致，没有把阶段 2—4 未执行的价值、竞品或方案结论伪装成事实，后续能力也都标记为候选而非 V0 承诺。修复上述 2 个 P1 后，战略/范围维度可进入最终校验。
