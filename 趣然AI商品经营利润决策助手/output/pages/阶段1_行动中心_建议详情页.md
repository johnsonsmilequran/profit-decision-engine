## 2. 页面概览

### 2.1 页面目标

本页是单条 SPU 经营建议从“为什么生成”到“谁审核、谁执行、结果如何”的唯一详情入口。页面必须让有权用户在同一条冻结业务事实下完成以下判断：

1. 明确建议针对哪个 SPU，而不是 SKU、广告计划或采购单。
2. 明确发现了什么经营问题、使用了哪些周期和口径的数据。
3. 沿固定规则查看“实际值 → 规则阈值 → 优先级处理 → 最终动作”的完整证据链。
4. 区分经营动作与库存动作，分别交给运营和采购计划执行。
5. 在 AI 不可用时，仍依靠结构化四要素完成审核、执行和结果记录。
6. 在历史模式中读取原批次事实，不受后续导入或规则版本变化影响。

### 2.2 页面唯一性

- 一个批次内一个 SPU 只对应一条建议详情。
- 当前任务与历史追溯复用同一页面和同一建议身份；历史入口只改变可操作性，不复制数据。
- 一条建议最多包含一个经营动作和一个库存动作；页面不允许增设第三条动作，也不允许人工改写规则结论。
- 页面总览状态只聚合双轨进度，不替代经营动作状态或库存动作状态。

### 2.3 成功衡量

| 衡量项 | 成功标准 |
| :--- | :--- |
| 四要素完整性 | 任何可读取的建议均完整展示具体对象、发现问题、关键依据、推荐动作，完整率 100% |
| 证据可追溯性 | 每条最终动作都能追溯到冻结指标、统计周期、采用值、阈值、比较关系和规则版本，覆盖率 100% |
| AI 降级可用性 | AI 生成中、失败或内容未采用时，审核、执行和结果记录仍可按状态继续，可用率 100% |
| 双轨独立性 | 经营动作与库存动作分别显示责任人、状态、版本、执行和结果，互不覆盖 |
| 历史一致性 | 新批次、新数据或新规则产生后，历史详情中的原快照与原结论变化数为 0 |
| 采购最小可见 | 采购计划响应与页面中出现完整利润、推广、品退、售后、完整 AI 或完整经营结果的字段数为 0 |
| 并发安全 | 过期版本覆盖已成功审核、执行或结果的次数为 0；同一重试产生重复成功业务事件的次数为 0 |

### 2.4 页面不做什么

- 不编辑导入数据、冻结指标、规则阈值、动作优先级或规则版本。
- 不把 AI 文本作为审核或执行的唯一依据，也不允许 AI 改写固定规则结论。
- 不提供批量审核、批量执行、批量结果回填或自动执行。
- 不直连或自动写入广告、采购、库存及其他外部业务系统。
- 不展示 SKU 级结论、广告明细、消费者个人信息、退款原因或评价原文。
- 不提供历史建议删除、覆盖或改写入口。
- 不允许运营主管拆分审核经营轨与库存轨。
- 不向采购计划展示通用历史入口、完整经营详情或其他角色的受限审计内容。

## 3. 用户与使用场景

### 3.1 角色目标与权限

| 角色 | 来本页的目标 | 可读取 | 可提交 | 明确禁止 |
| :--- | :--- | :--- | :--- | :--- |
| 运营 | 理解建议、执行经营动作、后补经营结果 | 完整销售、利润、推广、品退、库存、规则证据、AI 解读、审核结论、双轨状态、授权审计 | 经营动作执行；经营结果 | 审核建议；提交采购动作；修改规则或库存动作结论 |
| 运营主管 | 基于同一证据整体拍板，并追踪后续进度 | 完整建议、冻结指标、规则证据、AI 解读、双轨进度、完整审核范围内历史 | 待审核时整体通过或整体驳回；对 AI 解读重新生成 | 代运营或采购执行；拆分审核；修改动作结论 |
| 采购计划 | 判断并记录补货或禁补任务 | SPU 身份、补货/禁补结论、仓内库存、在途库存、近 14 天销量、日均销量、库存可售天数、采购任务状态与结果 | 补货执行；确认禁补；采购结果说明 | 完整利润、推广、品退、售后、完整 AI、完整经营结果；审核或经营动作 |

### 3.2 场景 A：主管整体审核一条双轨建议

- 时间：周一新批次规则计算完成后。
- 前置条件：建议状态为“待审核”；主管对该事业部和建议有权；建议同时包含“清仓”和“禁止补货”。
- 用户动作：主管从工作台进入详情，核对 SPU、批次、业务期间和截止日，查看“对象—问题—依据—动作”，沿规则证据链确认经营主动作由清仓优先级胜出、库存动作原子生成禁补；可展开 AI 辅助解读，但不依赖 AI 决定；提交整体通过或填写原因后整体驳回。
- 页面反馈：提交前再次确认“本次审核将同时作用于现有经营动作和库存动作”；成功后记录审核人、时间、结论和备注，双轨同时进入对应状态；若版本已变化，拒绝覆盖并展示最新结论、操作者和时间。
- 用户感受目标：能在一次判断中看懂动作来源和联动关系，不需要跨表格拼证据，也不会误以为可以只通过其中一轨。

### 3.3 场景 B：运营先执行经营动作，之后补录经营结果

- 时间：建议已整体通过后的周内执行与后续观察期结束后。
- 前置条件：经营动作处于“待执行”；当前用户是有权运营；库存动作可能仍由采购处理。
- 用户动作：运营确认加投、持续观察、SPU 整体推广止损或清仓动作，填写必要执行说明并提交；观察期结束后再次进入本页，填写观察期间、销售结果、利润结果、库存结果或明确标记“未提供”，再填写结果说明。
- 页面反馈：执行成功后经营轨进入“已执行”，库存轨保持自身原状态；补录结果后经营轨进入“已记录结果”。总览在一轨完成、一轨待处理时显示“执行中”，不错误显示“已完成”。
- 用户感受目标：动作执行和经营效果分开记录，既不会因当下没有结果而阻塞执行，也不会把“已执行”误当作“有效果”。

### 3.4 场景 C：采购计划确认禁补，不接触经营敏感信息

- 时间：主管整体通过后。
- 前置条件：建议包含库存动作“禁止补货”，该任务分配给当前采购计划人员。
- 用户动作：采购从采购工作台进入详情，只核对 SPU、库存动作、仓内/在途、近 14 天销量、日均销量和库存可售天数；确认已停止或不再安排补货，填写必要说明并提交。
- 页面反馈：库存轨记录“已确认禁补”、处理人、时间和说明；经营轨只显示不泄密的必要协同状态，不返回利润、推广、品退、完整 AI 或完整经营结果。
- 用户感受目标：拿到足够执行禁补的事实，同时不需要接触与采购职责无关的经营数据。

### 3.5 场景 D：AI 失败但业务闭环继续

- 时间：规则结论已生成，LiteLLM 暂时超时或返回越界内容。
- 前置条件：四要素、冻结指标、规则证据和双轨动作均已生成。
- 用户动作：运营或主管看到 AI 状态为“生成失败”或“内容未采用”，仍按固定规则继续审核或执行；必要时使用同一冻结数据重新生成解释。
- 页面反馈：失败原因使用业务可理解的受控说明，不展示原始模型输出或技术错误；重试不改变分类、指标、阈值、动作、审核或执行状态；重试期间保留上一版已采用解释。
- 用户感受目标：清楚 AI 是辅助说明而非决策门槛，不因 AI 异常停工。

### 3.6 场景 E：历史只读追溯一条部分完成的建议

- 时间：新批次已经产生后，运营或主管从历史列表进入旧建议。
- 前置条件：旧建议曾整体通过；经营轨已记录结果，库存轨仍待执行或曾出现冲突。
- 用户动作：查看旧批次的冻结业务期间、原指标、原规则版本、原动作和成功业务里程碑；按权限展开冲突等审计详情。
- 页面反馈：所有表单和提交动作不可用，并明确“历史只读”；页面不换算成新规则，也不使用当前批次指标替换旧值。
- 用户感受目标：能还原当时为什么这样决策、后来做到了哪一步，不把当前事实与历史事实混在一起。

## 4. 页面信息架构

### 4.1 内容顺序

1. **页面上下文**：返回来源、当前角色、事业部、SPU、批次、业务期间、业务截止日、规则版本、生成时间、历史只读标识。
2. **建议总览**：审核状态、经营动作状态、库存动作状态、只读聚合状态、数据限制摘要。
3. **结构化四要素**：具体对象、发现的问题、关键依据、推荐动作。
4. **规则证据链**：经营分类依据、实际值、采用值、周期、阈值、比较结果、命中条件、被覆盖条件、优先级和最终动作。
5. **冻结经营指标**：上一个完整自然月净销售额、表内经营准利润率、最近 7 天品退率及其质量信息、库存计算组成、上架时间与新品判断。
6. **双轨任务**：经营动作与库存动作分别显示结论、责任角色、当前状态、版本、执行记录和结果。
7. **AI 辅助解读**：默认收起，显示生成状态、采用状态、解释内容及允许角色的重新生成动作。
8. **当前角色操作**：主管整体审核；运营经营执行与经营结果；采购库存执行与采购结果；每次只显示当前角色和当前状态允许的表单。
9. **业务时间线**：建议生成、审核、经营执行、库存执行、结果记录等成功业务事件。
10. **审计详情**：按角色权限读取 AI 失败、越界内容未采用、并发冲突、重复请求、无权请求等受控事件。
11. **上下条与返回**：继承来源列表上下文，返回恢复原批次、页签、搜索、筛选、页码；上一条/下一条不脱离当前结果集。

### 4.2 信息层级约束

- 结构化四要素和固定规则证据始终先于 AI 解读，AI 不得成为唯一内容。
- 推荐动作必须同时给出经营动作和库存动作；某轨因规则不生成时，明确写出“不生成”及原因，不能留空造成误解。
- 总览状态只读，不能由用户直接选择；其变化只能来自整体审核及双轨各自事件。
- 业务时间线优先呈现成功业务里程碑；异常、冲突、重复请求和无权请求仅在有权限的审计详情中读取。
- 历史只读与当前可操作状态必须互斥；历史模式不出现可提交表单。

| 经营动作任务 | 动作、责任角色、状态、版本、执行人、执行时间、说明、结果 | 动作与追加事件 | 运营/主管 | 运营在允许状态提交；主管只读 |
| 库存动作任务 | 补货/禁补、必要库存依据、状态、版本、处理人、时间、说明 | 动作与追加事件 | 三角色按权限 | 采购在允许状态提交；禁补不可改成补货 |
| AI 辅助解读 | 生成中、已生成、生成失败、内容未采用及已采用解释 | AI 解释记录 | 运营/主管 | 默认收起；允许同冻结数据重新生成；采购不返回 |
| 主管审核栏 | 通过/驳回、审核备注、当前版本 | 审核状态 | 主管且待审核且非历史 | 整体审核；驳回原因必填；提交前二次确认 |
| 运营执行表单 | 执行动作确认、执行说明 | 经营轨 | 运营且已通过、待执行、非历史 | 观察动作说明必填；不允许改动作类型 |
| 经营结果表单 | 观察期间、销售、利润、库存结果、未提供标记、结果说明 | 经营轨 | 运营且经营动作已执行、结果未记录、非历史 | 结果可后补；未提供与具体值互斥 |
| 采购处理表单 | 补货执行或确认禁补、处理说明 | 库存轨 | 采购且已通过、待执行、被分配、非历史 | 不代表外部系统已回写；不允许改变结论 |
| 业务时间线 | 生成、审核、双轨执行、结果等成功事件 | 追加事件 | 按角色权限 | 只追加，不删除或覆盖 |
| 审计详情 | AI 异常、并发、重复请求、无权访问等受控信息 | 审计事件 | 有权且展开 | 按角色裁剪；不显示密钥、原始模型输出或敏感字段 |
| 上一条/下一条 | 当前结果集中的相邻建议 | 来源列表上下文 | 存在相邻项 | 继承当前批次和筛选；跨项前检查未提交表单 |

## 6. 交互与行为

### 6.1 进入与读取

1. 用户从工作台、行动清单或历史列表进入。
2. 页面每次读取均重新核验当前角色、事业部和建议对象关系。
3. 核验通过后按角色返回字段；采购计划只有在库存任务分配给本人且仍有权时才获得建议身份与必要数据。
4. 页面根据来源确定当前模式：当前任务模式允许按角色与状态操作；历史入口强制只读。
5. 页面恢复来源列表的批次、页签、搜索、筛选与页码上下文，用于返回和上下条导航。
6. 若工作区低于 1024px，提示使用电脑访问，并在关键金额、阈值、动作或状态可能无法完整读取时阻止正式提交。

### 6.2 主管整体审核

1. 仅运营主管且建议处于“待审核”时显示审核表单。
2. 主管选择“通过”或“驳回”；驳回必须填写原因，通过备注可选。
3. 提交前展示确认信息：SPU、当前规则动作、两条现有动作及本次结论。
4. 通过后，建议中的现有经营动作与库存动作同时生效并各自进入“待执行”；不会创建原规则未生成的动作。
5. 驳回后，两轨均进入关闭状态，原冻结数据、规则证据和推荐动作保留。
6. 页面追加唯一审核业务事件，并更新审核状态、双轨状态和总览状态。
7. 运营与采购计划不能通过直接地址、状态变更或历史入口获得审核能力。

### 6.3 运营执行经营动作

1. 仅运营、经营动作已通过且处于“待执行”时允许提交。
2. 表单只确认规则已给出的加投、持续观察、SPU 整体推广止损或清仓，不允许改选其他动作。
3. 持续观察动作的执行说明必填；其他动作说明可按需求填写。
4. 提交前再次确认；成功后记录执行人、时间、说明和新版本，经营轨进入“已执行”。
5. 库存轨状态保持不变；总览按双轨实际进度聚合。
6. 本页仅记录“运营已执行”，不声称广告或其他外部系统已自动完成写入。

### 6.4 运营补录经营结果

1. 经营动作已执行后才开放结果表单；结果记录与执行为两次独立提交。
2. 运营填写观察起止日期，并对销售、利润、库存结果分别填写具体值或标记“未提供”。
3. 同一结果项不能同时填写具体值和“未提供”。
4. 结果说明用于解释结果及后续判断，不允许倒改原动作或原规则证据。
5. 提交前再次确认；成功后追加结果事件，经营轨进入“已记录结果”。
6. 暂无结果不影响已执行状态，也不回退审核状态。

### 6.5 采购执行库存动作

1. 仅任务被分配的采购计划人员、建议已整体通过且库存轨处于“待执行”时允许提交。
2. 补货任务只能记录“已执行补货”及说明；禁补任务只能记录“已确认禁补/已停止补货”及说明。
3. 禁补结论不能在本页改为补货，补货结论也不能由采购改写。
4. 提交前再次确认；成功后记录处理人、时间、说明和新版本。
5. 本页记录采购协同行为，不等同于外部采购系统产生了订单或回执。
6. 经营轨状态保持不变，采购计划不获得经营结果表单。

### 6.6 AI 辅助解读与降级

1. AI 区默认收起；运营和主管可展开，采购计划不接收该区数据。
2. AI 状态包括“生成中、已生成、生成失败、内容未采用”。
3. 生成中不阻止固定规则、审核、执行或结果表单。
4. 失败时保留结构化四要素、规则证据和双轨动作，并提供受控失败说明。
5. 若 AI 输出出现冲突动作、虚构数值、广告明细、退款/评价原因、SKU 结论或其他越界信息，则整段标记“内容未采用”，不向用户呈现被过滤原文。
6. 运营和主管可请求重新生成；每次只使用同一冻结数据和规则结论，不读取当前新批次，不改变业务状态。
7. 重新生成期间保留上一版已采用解释；失败不覆盖上一版可用解释。

### 6.7 并发、重复提交与输入保护

1. 审核、执行和结果提交都携带页面读取到的当前业务版本。
2. 第一条合法成功更新生效；后续过期版本不得覆盖。
3. 若版本冲突，页面显示最新状态、最新操作者和时间，并保留用户尚未提交的输入供重新判断。
4. 网络中断后重试同一已成功请求时，返回已有成功结果，不重复追加业务事件。
5. 网络失败且请求未成功时，不改变业务状态，并保留表单输入。
6. 短表单不自动保存；用户带未提交内容返回、切换上下条或离开时先提醒。

### 6.8 历史只读

1. 从 `PAGE-F08-01` 进入时使用原建议身份打开同一详情页。
2. 所有指标、周期、规则版本、规则结论和建议动作读取原冻结快照。
3. 页面不出现审核、执行、结果或 AI 重新生成提交入口。
4. 成功业务里程碑继续显示；被驳回、部分执行、AI 失败或冲突不删除既有事实。
5. 审计详情仍按当前角色权限裁剪，采购计划不能借历史模式扩大字段范围。

### 6.9 导航

- 返回：回到来源页面并恢复原批次、页签、搜索、筛选和页码。
- 上一条/下一条：只在来源结果集内移动，不切换到未授权建议。
- 列表结果发生变化：若相邻项不再可访问，跳过该项；无相邻项时说明已到结果集边界。
- 表单未提交：返回、上下条、刷新或关闭前均提示，用户选择留在本页时保留输入。

### 7.2 边界场景

#### A. 网络边界

- 首次读取失败时不得显示“无建议”；保留来源和批次上下文，允许重试。
- 提交响应丢失时，重试应返回已有结果；不得产生第二条审核、执行或结果事件。
- AI 网络失败只影响 AI 区，不影响固定规则和业务动作。

#### B. 会话与权限边界

- 会话失效后立即停止展示经营数据；重新认证成功后仅返回原安全页面。
- 角色被撤销或更换后，旧页面的提交必须失败并重新投影字段。
- 采购通过猜测地址访问未分配建议时，不返回 SPU、建议是否存在、状态或其他可推断信息。

#### C. 数据质量边界

- 品退率缺分子、分母、周期或未验证时，明确显示质量限制；不得展示为可信 0%。
- 仓内、在途或近 14 天销量不足时，库存天数不伪造，补货结论按固定规则降级为“不生成”。
- 近 14 天平均日销量为 0 时不进行除法并不生成补货建议。
- 新品不生成补货建议，即使库存天数低于 30 天。
- 源值与采用值不一致时同时保留，并说明采用规则；不得静默覆盖。

#### D. 规则边界

- 同一 SPU 同时命中多个经营条件时，保留全部命中事实，按“清仓＞止损＞观察＞加投＞维持”只输出一个经营主动作。
- 被高优先级覆盖的低优先级条件仍可追溯，但不得被执行。
- 清仓或止损必须与禁止补货原子成对生成，不能只出现经营动作而缺少禁补。
- 加投可以与补货并存；这不是冲突，不得合并成一条动作。
- 系统没有足够事实时，不生成具体价格、内容或详情页优化结论。

#### E. 状态边界

- 待审核建议不能执行；已驳回建议不能重新执行原动作。
- 主管只能整体审核一次，不能对两轨分别通过或驳回。
- 运营执行后采购仍待处理时，总览为“执行中”。
- 经营动作已执行但尚无结果时，不能回退为“待执行”。
- 采购确认禁补后，不因运营结果变化自动改为补货。

#### F. 并发与重试边界

- 两位主管同时审核时，仅第一条合法提交成功。
- 两位运营或采购同时处理同一动作时，后提交者看到最新成功结果，不得覆盖。
- 过期页面提交结果时，保留用户输入，要求其读取新状态后重新判断。
- 同一请求的网络重试不得新增重复成功事件。

#### G. AI 边界

- AI 生成与审核可并行；AI 晚到不得改变已经完成的审核。
- AI 内容与固定动作冲突时，AI 整段不采用。
- AI 不得推断广告明细、退款原因、评价内容、SKU 结论或不存在的指标。
- 重新生成只基于原冻结数据；不能借重试使用本周更新值。
- 采购计划在当前和历史模式都不获取完整 AI 内容。

#### H. 历史边界

- 新批次导入不改变旧建议的指标、规则结论或事件。
- 新规则发布不对历史详情重算。
- 历史模式不允许通过直接调用恢复操作表单。
- 纠错若存在，只能以追加事件说明原值、修正值、操作者、时间和原因，不覆盖旧事实。

#### I. 输入与离开边界

- 驳回未填原因不得提交。
- 观察动作未填说明不得提交。
- 结果具体值与“未提供”同时存在时不得提交。
- 带未提交内容切换上下条、返回或离开时必须提醒。

## 8. 字段、口径与校验

### 8.1 冻结上下文字段

| 批次 ID | 本次导入与规则计算的唯一批次 | 必须 | 历史中不可替换 |
| 业务期间 | 上一个完整自然月，例如 2026-06-01 至 2026-06-30 | 必须 | 起止日期必须为完整自然月 |
| 业务截止日 | 批次事实截止日期 | 必须 | 用于新品时长与周期解释 |

| 数据质量摘要 | 字段缺失、未验证与降级结论 | 条件必需 | 缺失不得转为 0 |

### 8.2 冻结经营指标

| 字段 | 固定口径 | 证据要求 | 降级规则 |
| :--- | :--- | :--- | :--- |

| 库存可售天数 | （仓内库存＋在途库存）÷近 14 天平均日销量 | 组成值、采用值、计算周期 | 必要值缺失或日均为 0 时不展示伪造值 |

### 8.3 规则证据字段

| 字段 | 含义 | 要求 |
| :--- | :--- | :--- |
| 商品类型 | 大爆款、小爆款、新品或其他可判定类别 | 记录分类所用销售额与上架时长证据 |
| 实际值 | 本批次冻结的业务事实 | 带单位、周期、质量状态 |
| 源值 | 导入表中读取到的原值 | 与采用值并存，不静默覆盖 |
| 采用值 | 经口径标准化后进入固定规则的值 | 说明与源值差异或降级原因 |
| 规则阈值 | 对应规则版本的比较边界 | 历史按原版本展示 |
| 比较关系 | 大于、小于、区间或持续时长判断 | 与规则定义完全一致，不自行补含等号 |
| 命中条件 | 实际值与阈值比较后的结果 | 命中与未命中均可追溯 |
| 被覆盖条件 | 同时命中但因优先级未成为主动作的条件 | 标明“已被更高优先级覆盖” |
| 优先级 | 清仓＞止损＞观察＞加投＞维持 | 只用于经营主动作收敛 |
| 最终经营动作 | 清仓、止损、观察、加投或维持 | 一条建议唯一 |
| 最终库存动作 | 补货、禁止补货、不补货或不生成 | 与经营动作分轨保存 |
| 动作联动原因 | 如“清仓命中，因此原子生成禁补” | 清仓/止损时必须存在 |

### 8.4 结构化四要素字段

| 要素 | 最低内容要求 | 禁止内容 |
| :--- | :--- | :--- |
| 具体对象 | SPU 标识、商品链接或名称、所属批次 | SKU 级扩展结论 |
| 发现问题 | 明确说明增长机会、利润风险、品退风险或库存风险 | 只有“建议关注”等空泛描述 |
| 关键依据 | 指标值、统计周期、阈值、比较关系、数据限制 | 无周期数字、虚构指标、未声明的不确定值 |
| 推荐动作 | 唯一经营主动作、库存动作、责任角色和必要联动 | AI 新增动作、多个互相冲突的经营主动作 |

### 8.5 审核与执行字段校验

| 表单 | 字段 | 必填规则 | 校验与提交限制 |
| :--- | :--- | :--- | :--- |
| 整体审核 | 审核结论 | 必填 | 只允许通过或驳回；只在待审核状态提交 |
| 整体审核 | 审核备注 | 驳回必填，通过可选 | 驳回不得仅输入空白；不能包含对动作的人工改写 |
| 整体审核 | 审核版本 | 系统必带 | 过期版本拒绝覆盖 |
| 经营执行 | 执行动作 | 系统固定 | 必须等于规则最终经营动作，不可编辑 |
| 经营执行 | 执行说明 | 观察必填，其他可选 | 观察说明不得仅为空白；不能补造缺失证据 |
| 经营执行 | 执行版本 | 系统必带 | 过期版本拒绝覆盖 |
| 经营结果 | 观察开始/结束日期 | 必填 | 结束日不得早于开始日 |
| 经营结果 | 销售结果 | 值或“未提供”二选一 | 两者互斥；保留单位与期间 |
| 经营结果 | 利润结果 | 值或“未提供”二选一 | 两者互斥；利润率与利润金额不得混淆 |
| 经营结果 | 库存结果 | 值或“未提供”二选一 | 两者互斥；说明口径 |
| 经营结果 | 结果说明 | 必填 | 不得用于覆盖原规则动作 |
| 经营结果 | 结果版本 | 系统必带 | 已有成功结果时重试返回原结果 |
| 采购执行 | 采购动作 | 系统固定 | 补货只能确认补货执行；禁补只能确认禁补/停止补货 |
| 采购执行 | 处理说明 | 必填 | 不得仅为空白；不等同外部采购回执 |
| 采购执行 | 执行版本 | 系统必带 | 过期版本拒绝覆盖 |

### 8.6 状态口径

| 对象 | 状态集合 | 关键转换 |
| :--- | :--- | :--- |
| 建议审核 | 待审核、已通过、已驳回 | 待审核→已通过或已驳回；不可拆轨审核 |
| 经营动作 | 待审核、待执行、已执行、已记录结果、已关闭 | 整体通过后待执行；驳回后关闭；执行与结果分两次 |
| 库存动作 | 待审核、待执行、已处理、已关闭、不生成 | 整体通过后待执行；驳回后关闭；未生成轨不造任务 |
| 总览聚合 | 待审核、待执行、执行中、已完成、已驳回 | 只读聚合，不反向覆盖双轨 |
| AI 解读 | 生成中、已生成、生成失败、内容未采用 | 不驱动审核或动作状态 |

## 9. 页面流程与页面关系

### 9.1 主闭环

```text
工作台 / 行动清单
        │
        ▼
建议详情：读取角色投影 + 冻结事实 + 规则证据
        │
        ├─ 待审核 ──► 主管整体通过 ──► 经营轨待执行 + 库存轨待执行
        │                                  │                 │
        │                                  ▼                 ▼
        │                            运营执行动作        采购处理动作
        │                                  │                 │
        │                                  ▼                 │
        │                            运营补录结果             │
        │                                  └────────┬────────┘
        │                                           ▼
        │                                  总览按双轨聚合
        │
        └─ 待审核 ──► 主管整体驳回 ──► 双轨关闭，证据保留
```

AI 解读在固定规则结论之后异步存在；无论生成中、失败或内容未采用，均不切断上述闭环。

### 9.2 历史追溯关系

```text
PAGE-F08-01 历史与追溯列表
        │  携带原建议身份
        ▼
PAGE-F06-03 建议详情（历史只读）
        │
        ├─ 原批次冻结指标
        ├─ 原规则版本与证据链
        ├─ 原审核、执行与结果里程碑
        └─ 当前角色可见的审计详情
```

历史模式不建立第二条建议身份，不重新计算，不允许操作。

### 9.3 双轨关系

```text
同一条建议
├─ 经营动作轨：规则唯一主动作 → 运营执行 → 运营结果
└─ 库存动作轨：补货 / 禁补 / 不补货 / 不生成 → 采购计划处理

整体审核：一次作用于两条已存在动作
总览状态：只读聚合两轨，不替代两轨状态
```

### 9.4 导航关系与上下文继承

| 来源 | 进入目的 | 返回时恢复 | 特殊约束 |
| :--- | :--- | :--- | :--- |
| 运营工作台 | 处理经营待办或补录结果 | 当前批次与工作台任务位置 | 返回后任务状态同步 |
| 主管工作台 | 审核待办 | 当前批次、风险分组和位置 | 只允许整体审核 |
| 采购工作台 | 处理本人采购任务 | 采购页签和位置 | 不产生通用行动中心或历史权限 |
| 行动清单 | 查看或处理单条建议 | 批次、页签、搜索、筛选、页码 | 上下条限定于同一结果集 |
| 历史与追溯 | 还原旧建议 | 历史筛选和页码 | 强制只读 |

### 9.5 扩展约束

- 后续若引入 SKU，必须作为 SPU 下级对象重新进入 PRD；不得改变既有 SPU 建议身份和历史快照。
- 后续若接入广告、采购或库存系统自动回写，只能追加外部回执，不得覆盖人工业务事件与冻结规则证据。
- 后续新证据类型必须版本化，并保留当前“实际值—阈值—优先级—动作”的可追溯关系。
- 后续新增角色必须重新定义服务端字段投影，不能沿用“看得到页面就看得到全部字段”的权限方式。

### 10.1 页面读取数据

| 数据分组 | 最低数据内容 | 冻结或可变 | 角色边界 |

| 结构化建议 | 对象、问题、依据、经营动作、库存动作 | 冻结 | 采购仅库存任务投影 |

| 经营动作当前态 | 动作、状态、版本、执行与结果摘要 | 当前态可变，事件追加 | 采购不获取完整字段 |
| 库存动作当前态 | 动作、状态、版本、处理结果 | 当前态可变，事件追加 | 三角色按职责读取 |

| 审计详情 | AI、冲突、重试、无权等受控事件 | 只追加 | 按角色与对象关系裁剪 |

### 10.2 页面提交数据

| 提交类型 | 提交角色 | 最小提交内容 | 成功结果 |
| :--- | :--- | :--- | :--- |
| 整体审核 | 运营主管 | 建议身份、通过/驳回、备注、审核版本、确认 | 一条审核事件；两轨同时激活或关闭 |
| 经营动作执行 | 运营 | 建议身份、经营动作身份、执行说明、执行版本、确认 | 一条经营执行事件 |
| 经营结果 | 运营 | 动作身份、观察期间、三类结果或未提供、说明、结果版本、确认 | 一条经营结果事件 |
| 库存动作处理 | 采购计划 | 建议身份、库存动作身份、确认结果、说明、执行版本、确认 | 一条库存执行事件 |
| AI 重新生成 | 运营、运营主管 | 建议身份、原冻结解释版本 | 新解释尝试；不改变任何业务状态 |

### 10.3 明确不得提交或返回的数据

- LiteLLM 部署密钥、认证凭据、内部网关配置。
- 原始 AI 请求、被过滤的完整模型输出、底层技术错误堆栈。
- 完整 XLSX 文件内容或与本建议无关的行数据。
- 消费者个人信息、退款原因、评价原文、广告明细。
- SKU 级利润、库存、动作或从 SPU 推导出的 SKU 结论。
- 用户手工修改后的规则阈值、固定指标、主动作或库存动作。
- 采购计划无权查看的完整利润、推广、品退、售后、AI、经营结果与审计字段。
- 无权访问建议的身份、存在性、状态、责任人或历史事件。

### 10.4 数据一致性约束

- 冻结快照建立后不可被新导入、新规则、AI 重试或业务操作覆盖。
- 审核、执行和结果均以追加成功事件保留，当前状态由这些事件推进。
- 所有正式提交都校验当前角色、对象关系、允许状态和版本。
- 同一业务请求重试应复用已成功结果，不追加重复事件。
- 采购字段裁剪适用于正常读取、历史读取、错误响应、冲突响应和审计详情，不存在绕行路径。

| SEC-09 | 任一角色查看错误信息或审计详情 | 检查内容 | 不出现 LiteLLM 密钥、认证凭据、原始模型请求、完整被过滤输出或技术堆栈 |
| SEC-10 | 用户通过历史入口访问建议 | 尝试恢复表单或提交 | 历史模式保持只读，且字段权限不因历史入口扩大 |
| SEC-11 | 过期版本或重复请求到达 | 处理请求 | 不覆盖先前成功事实，不新增重复业务事件，并留下受控审计记录 |
| SEC-12 | 无法识别的角色访问页面 | 发起读取 | 默认拒绝，不降级为任一已知角色，也不返回经营数据 |

### 11.4 追溯与一致性验收

| 编号 | 验收条件 |
| :--- | :--- |
| TRC-01 | 每个最终动作均能从实际值、采用值、周期、阈值、比较、优先级追溯到结论。 |
| TRC-02 | 被覆盖的低优先级条件可见且明确标为未执行，不会成为第二个经营主动作。 |
| TRC-03 | 批次、业务期间、截止日、规则版本和生成时间在详情与历史中一致。 |
| TRC-04 | 审核、经营执行、库存执行和经营结果分别形成成功业务事件，事件不可删除或覆盖。 |
| TRC-05 | AI 失败、内容未采用、并发冲突、重复请求和无权请求按权限进入审计详情，但不污染成功业务时间线。 |
| TRC-06 | 新数据、新批次、新规则与 AI 重试均不会改变旧建议的冻结快照和原规则结论。 |

### 11.5 页面完成定义

本页只有在以下条件同时满足时才可判定完成：

1. 功能验收、体验验收、安全与权限验收、追溯与一致性验收全部有可复现证据。
2. 运营、运营主管、采购计划及无权角色四类账号均完成同一建议的权限验证。
3. 正常、AI 失败、字段降级、并发冲突、网络重试、历史只读六类关键路径均完成验证。
4. 采购字段裁剪覆盖正常、历史、错误、冲突和审计全部返回路径。
5. 未出现 SKU 级结论、外部系统自动写入、历史覆盖或 AI 取代固定规则的越界行为。
