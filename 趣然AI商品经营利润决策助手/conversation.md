# 趣然 AI 商品经营利润决策助手 · 对话记录

## 阶段 0 · 用户原始描述

趣然电商的销售、推广、库存、退款、评价和利润数据分散在不同系统及部门。运营和管理人员需要人工拉取数据、制作表格，再根据个人经验判断加投、广告止损、补货、清仓、价格或内容优化，以及退款、差评和质量问题如何反哺产品。信息分散导致问题发现滞后，经营动作之间缺少统一的利润判断标准。

目标是建立“AI 商品经营与利润决策助手”，自动汇总商品经营数据，按照增长机会、投放浪费、库存风险、售后风险和贡献利润生成每日行动清单。

首轮验证范围：选择一个事业部和 10—20 个真实 SKU，导入销售、推广、库存、退款及利润数据，识别至少 3 个真实经营问题，并输出可以执行的加投、止损、补货、清仓或优化建议。

## 已确认的商品判断标准

| 商品类型 | 类型条件 | 加投 | 观察 | 止损 | 补货 | 清仓 |
|---|---|---|---|---|---|---|
| 新品 | 上架不满两个月，优先于销售额分类 | 利润率 ≥-20% | 利润率 <-20% 且尚未满两个月 | 不单列 | 待后续确认 | 上架满两个月后仍不满足保留条件时按非新品规则判断 |
| 大爆款 | 非新品且月销售额 ≥10 万 | 利润率 ≥10% 且品退率 ≤1.5% | 未命中强动作时维持；品退率 >1.5% 时观察 | 0%≤利润率<5% | 库存可售天数 <30 天且未命中止损/清仓 | 利润率 <0% |
| 小爆款 | 非新品且月销售额 ≥2 万且 <10 万 | 利润率 ≥15% 且品退率 ≤1.5% | 未命中强动作时维持；品退率 >1.5% 时观察 | 5%≤利润率<10% | 库存可售天数 <30 天且未命中止损/清仓 | 利润率 <5% |
| 淘汰商品 | 非新品且月销售额 <2 万 | 不适用 | 不适用 | 不适用 | 禁止补货 | 淘汰清仓 |

### 动作冲突规则

- 主动作优先级：清仓 > 止损 > 观察 > 加投。
- 止损或清仓商品禁止补货；加投与补货可以同时输出。
- 未命中强动作的商品标记为“维持”，但不进入每日行动清单。
- 原“库存周转天数”正式改称“库存可售天数”。

## 阶段 1 · 已确认事实

### 最近一次真实案例

- 事业对象：布乐迪“忙碌屋”玩具，货号 515。
- 发生过程：前期采用亏损推广；直到财务提供月度利润报表后，运营才发现亏损较大并减少推广费用。
- 跨部门断点：运营减少推广时没有同步采购计划，采购仍按照此前销量继续补货。
- 最终结果：问题发现约延迟 2 个月；后期约滞销 3000 件，占用库存金额约 10 万元，产生利润损失约 6 万元。
- 产品启示：止损动作不能只作用于广告，还需要同步改变补货判断，避免经营动作互相抵消。

### 角色与责任

| 角色 | 查看清单 | 审核建议 | 执行动作 | 结果责任 |
|---|---|---|---|---|
| 运营 | 是 | 否 | 加投、广告止损、清仓 | 对销售额、利润和库存结果负责；首轮成果验收人 |
| 采购计划 | 是 | 否 | 补货 | 配合执行 |
| 运营主管 | 是，可查看完整利润、推广和售后信息 | 是 | 非主要执行者 | 负责建议审核 |

### 利润率口径

```text
首版利润率 = 商品链接表内“经营准利润率”
```

表内经营准利润率按净销售额与链接级销售成本、推广费、平台费、返现、售后费、赠品费、履约费、物流费、管理成本和其他费用计算；早先的“管理 8%+营销 7%+税 8%”自定义公式不作为首版判断口径。

### 首轮数据

- 首版只处理 SPU，SPU 即商品链接，不考虑 SKU。
- 试点事业部：玩具事业部。
- 数据来源：数据支持部门提供的表格。
- 首批文件已包含 10 个真实链接/SPU；销售、利润与费用期间为 2026-06-01 至 2026-06-30。

### 首轮产品闭环

```text
系统生成建议 → 运营主管审核 → 运营/采购计划分别确认执行 → 记录执行结果
```

- 不自动修改广告或采购系统。
- 目标是用人工确认的轻闭环解决运营止损与采购补货脱节，同时控制误操作和外部系统集成风险。

### 业务拍板、安全与 AI 权限

- 事业部负责人负责项目范围与资源投入拍板。
- 首轮经营数据不包含个人信息，允许发送给 AI 服务处理。
- 固定规则最终判定加投、观察、止损、补货和清仓动作；AI 不覆盖规则，只负责解释、排序和补充优化建议。
- 已有 LiteLLM 网关服务，由运维人员使用系统级部署密钥配置、维护和轮换；普通用户不可见。

### 经营指标补充口径

- 月销售额：自然月累计。
- 品退率：最近 7 天品退件数 ÷ 最近 7 天已销售件数。
- 库存可售天数：`(仓内库存数量 + 在途库存) ÷ 最近 14 天平均日销售量`。

### 数据节奏与权限

- 数据支持部门每周一提供一次经营表格。
- 每周一导入新数据后生成一次新行动清单；一周内每天只更新审核、执行和结果状态，不重复生成同数据的新判断。
- 新品首版不生成补货建议。
- 采购计划只查看补货/禁补结论，以及库存、销量等必要依据。
- 完整利润、推广和售后数据仅运营与运营主管可见。

### 商品分类与 LiteLLM 配置

- 非新品使用上一个完整自然月销售额判断大爆款、小爆款和淘汰商品；新品仍优先按上架不满两个月判断。
- LiteLLM 由运维通过系统级部署密钥配置，作用于本产品环境。
- 普通用户不可查看凭据；更新和轮换由运维负责。
- 首版不建设管理员后台配置或用户自助配置能力。

## 阶段 1 · 商品链接.xlsx 核验

- 用户确认：一个商品链接相当于一个 SPU，可包含多个 SKU；费用按链接/SPU 核算，不按 SKU 核算。
- 文件包含 10 条唯一商品链接、78 列链接经营字段，未包含 SKU、货号、规格、仓内库存、在途库存或 SPU—SKU 映射。

- 第 1 行合计与 10 条可见明细不一致；上架时间和部分布尔字段存在错位或混合值。
- 详细证据见 `evidence/商品链接字段核验.md`。

## 阶段 1 · SPU 范围与数据期间确认

- 当前项目只考虑 SPU，SPU 与商品链接一对一；首版取消 SKU 映射、SKU 利润分摊和 SKU 级经营动作。
- 首版固定规则采用表内“经营准利润率”。

## Admin 管理后台增量 Feature · 阶段 0

- 用户确认临时 SQL 和“联系运维”不足以支持产品实际使用，正式要求新增系统管理后台和 admin 管理员能力，由管理员在产品内维护用户角色。

- 该需求正式覆盖旧 PRD 中“不提供业务侧角色管理后台”的边界，但仍坚持钉钉为唯一身份入口，不自动把未映射用户提升为管理员。

## Admin 管理后台增量 Feature · 阶段 1 前沿 1

- 现有实现事实：业务角色是 `operations/supervisor` 二选一枚举；会话必须从有效 `role_mapping` 创建；无映射回调直接进入 `no_role` 恢复页；当前不存在 admin 路由、管理权限或待审批身份状态。
- 本轮需用户拍板：Admin 认证方式、Admin 权限与业务角色关系、未授权身份进入待审批流程的方式。

### 用户拍板

- Admin 采用独立本地用户名密码登录，不依赖钉钉认证。
- Admin 管理权限与运营、运营主管业务角色正交；管理权限本身不等于经营业务数据权限。
- 钉钉认证成功但没有有效业务角色的身份自动生成待审批申请，等待 Admin 处理，不自动授予角色。

## Admin 管理后台增量 Feature · 阶段 1 前沿 2

- 本地 Admin 认证引入独立高权限凭据，下一前沿需确认首位管理员安全初始化与二次验证要求。
- 管理权限已确认与业务角色正交，下一前沿可独立确认 Admin 默认是否读取经营业务数据。

### 用户拍板

- 系统没有管理员时，使用部署配置的一次性初始化口令进入 `/admin/setup` 创建首位管理员；创建成功后关闭初始化入口，不提供固定默认账号密码。
- Admin 默认不能读取经营业务数据；只有另行获得运营或运营主管角色后，才能进入相应业务页面。
- 本地 Admin 强制使用身份验证器动态码，并在绑定时生成一次性恢复码。

## Admin 管理后台增量 Feature · 阶段 1 前沿 3

- 首位管理员与二次验证方式已确定，下一前沿先确认其他管理员的创建和撤销；该答案随后决定账号恢复可否依赖其他管理员。

### 用户拍板

- 系统只保留首位 Admin，不允许 Admin 在后台创建或委派其他 Admin。
- 事业部负责人继续负责运营、运营主管业务角色审批；Admin 只按已审批结果执行配置，并记录审批人和审批依据。

## Admin 管理后台增量 Feature · 阶段 1 前沿 4

- 单管理员模型减少了委派攻击面，但形成高权限账号单点失效；下一前沿需确认忘记密码或丢失动态码时的恢复机制，以及唯一管理员不可停用保护。
- 核心功能和安全边界已基本收敛，下一前沿需为该增量 Feature 确认可观察的成功标准和验证时间窗。

### 用户拍板

## Admin 管理后台增量 Feature · 技术可行性预检

- 现有 `business_role` 仅允许 `operations/supervisor`，且 `user_session` 必须引用有效 `role_mapping`；因此 Admin 不能作为第三种业务角色，也不能复用业务会话。
- 可行方案是在同一 Go API 与 PostgreSQL 内增加独立 Admin 账号、会话、待审批身份和不可变管理审计模型；业务 API 继续只接受钉钉业务会话，Admin API 只接受独立 Admin 会话。
- 钉钉回调已在创建业务会话前取得稳定 `actor_ref`，可在无有效角色时按该键幂等写入待审批身份，再保持拒绝业务访问。
- 初始化、恢复和 TOTP 需要新增部署秘密、哈希/加密存储、一次性消费记录、并发单例约束、CSRF 防护与会话全量撤销；现有 Go/PostgreSQL/React 技术栈均可支撑。
- 现有 `business_event` 绑定经营任务，不适合管理审计；需新增独立、禁止更新删除的 `admin_audit_event`。
- 当前钉钉客户端只保留 `unionId`，待审批列表若要显示姓名，需扩展当前用户响应字段或提供安全降级显示；该点不阻塞核心授权闭环。
- AI 预检结论为 F09 可在现有架构内实现且无需收缩已确认产品范围；详细证据见 `evidence/technical-feasibility.md`。

## Admin 管理后台增量 Feature · 阶段 3 调研

- 已完成 8 个直接/间接竞品研究：Microsoft Entra、Okta、SailPoint、JumpCloud、Authing、阿里云 IDaaS、飞书管理后台和 Shopify Admin；完整结果见 `evidence/competitors.md`。
- 已核验行业与安全基线：NIST 最小权限、职责分离、账号变更审计和恢复要求，OWASP 日志保护，Google Cloud IAM 权限传播时延，以及 Okta 委托 Forrester 的身份治理经济研究；完整结果见 `evidence/benchmark.md`。
- 核心结论是保持单 Admin、两个固定业务角色的产品内最短闭环，不建设通用 IAM；单一恢复口令不能宣称符合 NIST AAL2，必须保留已确认的一次性消费、旧会话撤销和审计，并在方案阶段补明高熵、短时效、运维审批与恢复通知。
