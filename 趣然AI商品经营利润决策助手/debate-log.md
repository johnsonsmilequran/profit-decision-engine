# F09 Admin 管理后台 · 阶段 4 多角色评审记录

> 本文件保留 V0 到 V1 的意见、响应和相互 challenge。评审结论不自动替代用户已经确认的产品边界。

## Round 0 · Lead PM V0

- 输入：`scene-anchor.md`、`assumptions.md`、`evidence/technical-feasibility.md`、`evidence/competitors.md`、`evidence/benchmark.md`。
- 输出：`proposal-v0.md`。
- 核心主张：首版完成“钉钉认证—幂等待审批—外部审批—唯一 Admin 配置—唯一角色生效—进入工作台—全程审计”的最小闭环。
- 待评审决策：审计留存、恢复通知、审批依据最小格式。

## Round 1 · 四方独立评审

四位评审在互不查看其他首轮意见的条件下完成。

### 工程评审

**结论：技术可行，但 V0 必须修订后才能进入实现设计。无不可实现的致命问题。**

| ID | 级别 | 意见 |
|---|---|---|
| T1 | 阻塞 | 部署恢复口令不能只是环境变量；需有摘要、版本/指纹、签发、过期、消费和环境状态，数据库快照恢复后旧口令不得复活。 |
| T2 | 阻塞 | 恢复通知是单口令恢复的补偿控制，必须升为 P0/上线门禁；不能发送时不得静默完成。 |
| T3 | 阻塞 | 保存型恢复码与部署恢复的权限、失效项和会话撤销语义必须分开；凡能重设密码/TOTP 均需递增凭据版本并撤销旧会话。 |
| T4 | 阻塞 | 单 Admin 不能被登录失败永久锁死；采用渐进限速/短时冷却，部署恢复不受普通登录失败锁死。 |
| T5 | 阻塞 | 角色变更、该身份业务会话撤销、审批记录和审计事件必须同事务；验收同时检查会话不可用和已标记撤销。 |
| T6 | 阻塞 | 审计威胁边界需明确；运行账号无更新/删除/DDL 权限，权限变更与审计同事务，审计失败则回滚。 |
| T7 | 阻塞 | Admin 与业务 Cookie 同时存在时仍禁止 fallback、身份转换或共享令牌秘密；双 Cookie 隔离需必测。 |
| T8 | 阻塞 | 授权主键至少包含身份提供方、企业作用域和稳定用户标识；姓名仅辅助展示，身份不足时不得授权。 |
| T9 | 阻塞 | 开发与线上初始化/恢复秘密必须使用不同配置源和命令入口，禁止进入仓库、镜像、前端包或日志。 |
| T10 | 阻塞 | 10 分钟以服务端事件计时：初始化开始到目标用户建立正确业务会话并访问工作台；外部审批等待不计入。 |
| T11 | 阻塞 | TOTP 密文需带密钥版本并定义轮换/备份恢复语义；恢复重绑后旧 TOTP 立即失效。 |
| T12 | 阻塞 | 三年价值窗口不能推导审计留存；期限、在线留存、归档和清理需由治理要求决定。 |

非阻塞但必须进入技术设计：会话绝对/空闲时长、CSRF + Origin、失败事件限流、待审批生命周期重开规则、恢复演练、审计分页索引和“错误授权 0”的约束化验收。

### 设计评审

**结论：不通过，存在两个用户闭环级阻塞问题。**

| ID | 级别 | 意见 |
|---|---|---|
| D1 | 致命 | 自动建申请后若无具体责任人、联系方式和 Admin 可发现机制，只是把错误页换成“申请已生成”的新死路。 |
| D2 | 致命 | opaque 标识、同名或姓名缺失时无法防止错人；必须定义至少两个可核验身份属性，不足时阻止授权。 |
| D3 | 阻塞 | 状态需拆成待取得外部审批、已取得审批待 Admin 配置、已配置待重新登录、已授权、已停用和配置冲突；产品不能伪装知道外部审批进度。 |
| D4 | 阻塞 | “已配置需重新登录”和会话失效反馈必须由 P1 升为 P0。 |
| D5 | 阻塞 | `/admin/recovery` 需定义无效、过期、已消费、时钟异常、密码不合规、网络中断及成功落点。 |
| D6 | 阻塞 | 初始化必须完成 TOTP 实码验证、恢复码保存确认、刷新/返回处理和首次登录验证。 |
| D7 | 阻塞 | 新增、变更、停用、恢复须使用不同高风险确认文案，并明确会话影响。 |
| D8 | 阻塞 | 用统一身份生命周期详情承载当前状态、核验信息、审批依据、当前角色、历史和最近审计，避免对象保存后无解释地消失。 |

设计要求：首版禁止批量授权；提交确认同时突出人员、稳定身份摘要、前后角色、审批依据和会话影响；页面继承既有 PC 设计体系并提供可操作错误恢复。

### 商业评审

**结论：方向成立，但运营与价值闭环未成立，阻塞定版。**

| ID | 级别 | 意见 |
|---|---|---|
| B1 | 阻塞 | 唯一 Admin 的实际岗位、日常响应、离岗交接、恢复审批人和响应责任未明确。 |
| B2 | 阻塞 | 72 万元/年和 216 万元三年缺少 F09 专属归因规则，不能把发现、审核、执行等其他延误全部算给 F09。 |
| B3 | 阻塞 | 10 分钟只证明首次配置；还需分开记录日常配置处理时间和含外部审批的完整授权周期，不擅自编造目标。 |
| B4 | 阻塞 | 恢复通知不能留在 P1；它是上线所需安全补偿控制。 |
| B5 | 阻塞 | 上线门禁需包含 Admin 人选、首位审批材料、TOTP、通知对象、初始化与恢复演练。 |
| B6 | 严重 | 审计留存由治理要求决定，不能由价值周期倒推。 |
| B7 | 严重 | 年度价值验证需明确事件台账责任人、重算时间与证据。 |
| B8 | 严重 | 积压可发现性和责任承接必须属于 P0，否则“待审批”仍无人处理。 |
| B9 | 严重 | 审批依据要定义组织认可的证据类型和不可接受情形。 |

商业口径：72 万元/年是待验证潜在风险暴露，216 万元是频率与单次影响持续三年的可支撑价值上限；F09 只纳入“因缺少有效角色无法进入且导致经营动作延误”的事件，不作为独立收入、增长或拉新功能。

### 战略评审

**结论：有条件通过；现在必须解锁系统，但只建设“能安全开门”的能力。**

| ID | 级别 | 意见 |
|---|---|---|
| S1 | 阻塞 | F09 是整套产品兑现潜在经营价值的必要解锁条件，不能独占 216 万元价值。 |
| S2 | 阻塞 | V0 有滑向小型 IAM 的风险；首发只保留首次授权或防止高危越权所必需的能力。 |
| S3 | 阻塞 | 单 Admin 是当前策略约束而非永恒身份模型；需定义未来重评触发器并保护审计与历史可迁移性。 |
| S4 | 阻塞 | 审批、Admin、运维三处人工依赖必须明确具体岗位、替补机制和响应责任。 |

战略建议：上线 30 天复盘真实申请量、外部审批时间、产品内处理时间、误授权和恢复演练；出现第二生产环境、第三业务角色、跨事业部审批、申请量越过门槛、唯一 Admin 离岗或首次恢复失败时，重评单 Admin 及 OA/IDaaS 集成。

## Controller 首轮合并判断

四方独立意见形成五个交集：

1. **待审批不能只是状态页**：必须有具体责任承接、Admin 可发现性和用户可执行下一步。
2. **恢复通知是 P0**：它不是体验增强，而是单口令恢复的安全补偿控制。
3. **身份核验是零错授前提**：稳定作用域主键 + 可与审批材料对应的组织属性不足时，禁止授权。
4. **价值必须收敛归因**：F09 仅作为整套产品的解锁条件，不能认领全部经营价值。
5. **单 Admin 需运营化且可重评**：当前不新增第二 Admin，但必须有具体岗位、交接/恢复责任和未来升级触发器。

需要 Lead PM 在 V0.5 逐项给出接受、拒绝或暂缓，并说明理由；不得用“后续设计细化”回避影响上线闭环的意见。
