# 场景锚点 V1 · Admin 管理后台增量 Feature

**产品名**：趣然 AI 商品经营利润决策助手  
**增量 Feature**：F09 · Admin 管理后台与业务角色配置  
**一句话定位**：为钉钉已认证但尚无业务角色的员工提供一条由事业部负责人审批、唯一 Admin 安全配置、全过程可审计的产品内授权闭环。

## 用户与角色

- **直接使用者**：唯一 Admin，负责查看待审批身份、核对审批依据、配置或调整运营/运营主管角色、停用或恢复业务授权并查看审计记录。
- **业务审批人**：事业部负责人，负责批准业务角色；不直接操作 Admin 后台。
- **业务用户**：通过钉钉认证的运营或运营主管；没有有效角色时只能进入待审批状态，不能访问业务数据。
- **不是谁**：Admin 不是业务审批人，也不是天然的经营数据超级用户；普通业务用户不能创建 Admin 或自行修改角色。

## 场景与当前替代方案

- **触发场景**：员工完成钉钉身份认证，但系统找不到唯一有效业务角色。
- **当前行为**：系统显示“已确认身份，但没有找到唯一有效角色”，用户无法进入产品。
- **当前替代方案**：联系运维后直接修改数据库或配置文件。
- **替代方案问题**：空角色环境没有任何人能进入系统完成配置；过程依赖技术人员、缺少产品内审计，也无法形成稳定的首次使用流程。

## 核心痛点

- 钉钉认证成功不等于已获得业务授权，现有产品缺少认证后的授权闭环。
- 新环境没有角色映射时，全部业务用户均被挡在系统外。
- 直接改数据库无法成为日常管理方式，且审批责任、配置责任和操作证据容易混淆。

## 成功定义

- **基线**：当前空角色环境无法通过产品界面创建 Admin 或授予首个业务角色，完成时间不可控。
- **首用目标**：从打开初始化页面，到一个已获事业部负责人批准的钉钉用户取得正确业务角色并成功进入对应工作台，全流程不超过 10 分钟。
- **安全护栏**：错误业务授权为 0；所有 Admin 登录恢复、角色新增、修改、停用和恢复操作均有审计记录。
- **验证时间窗**：首次部署和首次授权闭环当次验证。

## 第一版范围

### 必须做

- 系统无 Admin 时，使用部署配置的一次性初始化口令进入 `/admin/setup` 创建唯一 Admin；成功后立即关闭初始化入口并使口令失效。
- Admin 使用独立本地用户名密码登录，强制绑定身份验证器动态码，并生成一次性恢复码。
- 钉钉认证成功但无有效业务角色的身份自动生成或更新一条待审批申请，不自动授予任何角色。
- Admin 依据事业部负责人已经完成的审批，为身份分配唯一的运营或运营主管角色，并记录审批人和审批依据。
- Admin 可修改、停用和恢复业务角色映射；所有高权限操作均可审计。
- Admin 默认不能读取经营业务数据；只有另行获得相应业务角色后，才能进入对应业务页面。
- 唯一 Admin 无法登录时，由运维配置一次性恢复口令，通过 `/admin/recovery` 重设密码和动态码；成功后撤销旧会话并销毁恢复口令。
- 唯一 Admin 不允许在管理后台停用或删除自己。

### 明确不做

- 不允许在后台创建、委派或保留第二个 Admin。
- 不让 Admin 代替事业部负责人审批业务角色。
- 不提供默认 Admin 账号密码，不自动把首个钉钉用户提升为 Admin。
- 不允许一个业务身份同时拥有运营和运营主管两个有效角色。
- 不因 Admin 身份自动开放经营数据或业务操作权限。
- 第一版不对接独立 OA 审批 API；审批结果由 Admin 核对并记录依据。

## 外部能力与配置责任

| 能力/配置 | 状态与责任 | 入口与作用域 | 生命周期 |
|---|---|---|---|
| 钉钉统一身份认证 | 已有能力，由运维维护 Client 配置 | deployment-secret，系统级 | 按既有钉钉凭据轮换规则维护 |
| Admin 初始化口令 | 内部部署运维生成并配置 | deployment-secret，系统级；产品入口 `/admin/setup` | 仅系统无 Admin 时有效，成功创建后立即失效 |
| Admin 恢复口令 | 内部部署运维按需生成并配置 | deployment-secret，系统级；产品入口 `/admin/recovery` | 单次使用，成功恢复后立即失效并撤销旧会话 |
| 身份验证器动态码 | Admin 使用兼容 TOTP 的身份验证器绑定 | onboarding/admin，用户级 | 初始化或恢复时绑定，密钥不可明文回显 |

## 关键约束与风险接受

- 复用现有钉钉身份与 `operations/supervisor` 业务角色模型，F09 不改变经营规则或业务数据范围。
- 用户明确选择单 Admin 模型，接受其单点失效代价；通过一次性恢复口令降低完全锁死风险。
- 初始化口令、恢复口令、密码、TOTP 密钥和会话令牌均属于敏感凭据，不得进入前端静态包、业务 API 响应、日志或审计详情。
- 高权限操作必须使用独立 Admin 会话，不得借业务用户 Cookie 代替。

## 最大不确定性

- 单 Admin 模型依赖运维能够在凭据丢失时及时、安全地配置一次性恢复口令；这是用户已接受的运营风险，需在后续技术可行性预检中验证现有部署配置能否无常驻后门地支持。

## 最不该做的方向

- **不要把 Admin 做成全能超级用户**：这会把身份管理、业务审批和经营数据访问集中到一个本地高权限账号，推翻已经确认的职责分离和最小权限边界。

## 假设清单

- 当前没有阻塞阶段 2 的未确认假设；单 Admin 单点风险和部署恢复责任均已由用户明确接受。

## 价值论证（阶段 2 已确认）

- **用户最终判断**：认可 F09 解锁整套经营决策助手后能够支撑约 200 万元价值，但保留年度数量与三年持续性的验证要求。
- **受益方**：事业部/公司；价值不是单次运维配置效率，而是让已完成钉钉认证的业务用户能够获得角色并实际使用整套经营决策助手。
- **当前代价口径**：按 515 历史案例，每个类似经营问题因发现或授权延误造成约 6 万元直接利润损失；约 10 万元库存占用只作风险佐证，不重复相加。
- **可影响规模**：暂无完整年度记录，暂按用户确认的待验证假设值 12 次/年计算。
- **价值结果**：约 72 万元/年的受影响利润，按三年口径可支撑约 216 万元价值；该金额不得表述为已经实际节省。
- **最锋利的话**：没有 Admin，整套经营决策助手的价值不是打折，而是归零。
- **验证要求**：上线后按管理审计与经营问题事件台账逐年统计实际次数和实际利润影响；若 12 次/年或三年持续性不成立，必须同步重算并下调价值。
