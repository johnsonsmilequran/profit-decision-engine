# 趣然 AI 商品经营与利润决策助手 PRD V0

## 0. 版本定位与首版定义

| 项目 | 内容 |
|---|---|
| 文档版本 | V0 · 范围收敛稿 |
| 试点范围 | 玩具事业部，10—20 个真实 SPU |
| 决策对象 | SPU，即商品链接；不处理 SKU |
| 数据节奏 | 每周一导入新表后生成一次新行动清单 |
| 执行模式 | 轻闭环：系统建议、人工审核、人工执行、系统记录结果 |
| 首轮完成定义 | 导入 10—20 个真实 SPU，识别至少 3 个真实经营问题，每条建议说明对象、问题、关键依据和推荐动作 |

> 本版以已确认的链接/SPU 经营数据为边界。数据源不提供的评价文本、退款原因和广告计划明细不进入首版。

## 1. 项目背景

趣然电商的销售、推广、库存、退款、品退和利润数据分散在不同系统和部门。运营和管理人员需要人工拉取数据、制作表格，再根据个人经验决定：

- 哪些商品应该增加投放；
- 哪些商品应该减少或停止推广；
- 哪些商品需要补货、禁止补货或清仓；
- 哪些商品存在品退或质量风险；
- 哪些问题需要由运营、采购计划或运营主管处理。

信息分散导致问题发现滞后，不同部门的动作缺少统一的利润判断标准。

### 1.1 真实案例

布乐迪“忙碌屋”玩具（货号 515）前期以亏损方式推广。运营直到财务提供月度利润报表后才发现亏损较大，问题发现约延迟 2 个月。运营随后减少推广费用，但未同步采购计划，采购仍按旧销量补货，造成约 3000 件滞销、占用库存金额约 10 万元、利润损失约 6 万元。

> 核心问题不只是“没有看到亏损”，而是止损、推广和补货没有形成同一套决策。

## 2. 产品目标

建立一个“AI 商品经营与利润决策助手”，按周汇总 SPU 销售、推广、品退、利润和可用的库存数据，使用固定规则生成行动结论，再由 AI 输出易读解释和优先级排序。

### 2.1 首版目标

1. 让运营在每周数据到达后，直接看到需要加投、观察、止损、清仓或维持的 SPU。
2. 让运营主管基于同一组数据审核建议，而不是依赖个人经验。
3. 让采购计划同步看到补货或禁止补货结论，避免运营止损后继续扩大库存。
4. 让每个经营动作有对象、问题、依据、责任人和执行状态。

### 2.2 非目标

- 不自动修改广告投放、采购计划或库存系统。
- 不处理 SKU，不建立 SPU—SKU 映射，不计算 SKU 利润。
- 不做评价文本分析、差评主题归因或商品内容自动优化。
- 不做退款/退货原因归因。
- 不定位到广告计划、单元、关键词或素材；推广止损只到 SPU 整体粒度。
- 不允许 AI 改写或覆盖经营阈值。
- 不建设 LiteLLM 密钥管理后台或普通用户配置页。

## 3. 产品角色与权限

| 角色 | 可见数据 | 主要操作 | 责任 |
|---|---|---|---|
| 运营 | 销售、利润、推广、品退、库存和全部建议 | 导入/查看清单，执行加投、SPU 推广止损和清仓，更新执行与结果状态 | 对销售额、利润和库存结果负责；首轮验收 |
| 运营主管 | 销售、利润、推广、品退、库存和全部建议 | 审核、通过、驳回建议 | 对建议审核负责 |
| 采购计划 | 仅补货/禁止补货结论及库存、销量等必要依据 | 执行补货，更新执行状态 | 对补货执行负责 |
| 事业部负责人 | 不作为首版日常操作角色 | 对项目范围和资源投入拍板 | 业务决策者 |

## 4. 核心使用流程

```text
数据支持部门每周一提供 SPU 经营表
  → 运营导入并完成字段校验
  → 固定规则计算商品类型与经营动作
  → AI 解释问题、提取关键依据并排序
  → 生成本周行动清单
  → 运营主管审核
  → 运营/采购计划执行
  → 一周内更新执行和结果状态
```

- 同一批数据只生成一份行动清单。
- 周内可每日更新审核、执行和结果状态，不基于原数据重复生成新建议。
- 新数据到达后生成新清单，历史清单保留且不被覆盖。

## 5. 数据范围与口径

### 5.1 首版数据粒度

- 一行代表一个 SPU/商品链接。
- SPU/商品链接是所有规则计算、建议、审核和执行记录的唯一商品粒度。
- 不读取 SKU 字段，不向下拆分成本、销量或库存。

### 5.2 必需字段

| 字段组 | 必需字段 | 用途 |
|---|---|---|
| SPU 身份 | 链接 ID/SPU ID、链接名称、店铺、平台、运营、上架日期 | 唯一识别、新品判断、责任归属 |
| 销售 | 扣除退款后的净销售额、销量、订单数 | 商品分类和依据展示 |
| 利润与推广 | 经营准利润率、经营准利润值、推广费用 | 加投、止损和清仓判断 |
| 品退 | 品退件数、已销售件数或品退率 | 观察和售后风险判断 |
| 库存（条件必需） | 仓内库存、在途库存、最近 14 天销量 | 库存可售天数和补货判断 |

### 5.3 统计周期

| 指标 | 口径 |
|---|---|
| 商品分类销售额 | 上一个完整自然月的净销售额 |
| 经营准利润率 | 上一个完整自然月，直接采用数据支持表中的“经营准利润率” |
| 品退率 | 最近 7 天品退件数 ÷ 最近 7 天已销售件数 |
| 库存可售天数 | `(仓内库存 + 在途库存) ÷ 最近 14 天平均日销量` |
| 首批样本期间 | 2026-06-01 至 2026-06-30；原表头“上一周”视为错误标注 |

### 5.4 经营准利润率

首版不按早先的“管理费 8%+营销费 7%+税率 8%”公式重算，而是直接采用商品链接表中的经营准利润率。

样本表中的经营准利润值可按以下字段复算：

```text
净销售额
- 链接销售成本
- 推广费用
- 平台费用
- 返现费用
- 售后费用
- 赠品费用
- 履约费用
- 产品物流费用
- 综合管理成本
- 其他费用
= 经营准利润值
```

```text
经营准利润率 = 经营准利润值 ÷ 净销售额
```

## 6. 商品分类规则

系统先判断是否为新品，再对非新品按上一个完整自然月净销售额分类。

| 商品类型 | 判定条件 |
|---|---|
| 新品 | 当前日期距上架日期不满 2 个月 |
| 大爆款 | 非新品，且上一个完整自然月净销售额 ≥10 万元 |
| 小爆款 | 非新品，且上一个完整自然月净销售额 ≥2 万元且 <10 万元 |
| 淘汰商品 | 非新品，且上一个完整自然月净销售额 <2 万元 |

若上架日期缺失或无法解析，该 SPU 不自动分类，标记“数据异常”并等待运营修正。

## 7. 经营动作规则

### 7.1 动作优先级

```text
清仓 > 止损 > 观察 > 加投 > 维持
```

- 同一 SPU 只有一个主动作。
- 清仓或止损时必须同时输出“禁止补货”。
- 加投可以与补货建议同时存在。
- 未命中主动作的 SPU 标记为“维持”，默认不进入行动清单。

### 7.2 新品

| 条件 | 主动作 | 补货动作 |
|---|---|---|
| 经营准利润率 ≥-20% | 加投 | 首版不生成补货建议 |
| 经营准利润率 <-20% | 观察 | 首版不生成补货建议 |

新品上架满 2 个月后，不再使用新品规则，转入非新品销售额分类。

### 7.3 大爆款

| 条件 | 主动作 |
|---|---|
| 经营准利润率 <0% | 清仓 |
| 0%≤经营准利润率 <5% | 止损 |
| 品退率 >1.5% | 观察 |
| 经营准利润率 ≥10% 且品退率 ≤1.5% | 加投 |
| 其他 | 维持 |

### 7.4 小爆款

| 条件 | 主动作 |
|---|---|
| 经营准利润率 <5% | 清仓 |
| 5%≤经营准利润率 <10% | 止损 |
| 品退率 >1.5% | 观察 |
| 经营准利润率 ≥15% 且品退率 ≤1.5% | 加投 |
| 其他 | 维持 |

### 7.5 淘汰商品

- 主动作：淘汰清仓。
- 补货动作：禁止补货。

### 7.6 补货规则

对非新品，只有当主动作不是止损或清仓时，才计算补货建议：

| 条件 | 动作 |
|---|---|
| 库存可售天数 <30 天 | 补货 |
| 库存可售天数 ≥30 天 | 不补货 |
| 仓内、在途或最近 14 天销量缺失 | 不生成补货建议，标记“库存数据不足” |
| 最近 14 天平均日销量为 0 | 不除以 0；不生成补货建议，标记“无近期销售” |

## 8. 行动清单与建议结构

每条建议至少包含以下内容：

| 字段 | 具体含义 | 示例 |
|---|---|---|
| 具体对象 | 链接 ID/SPU ID、链接名称、店铺、责任运营 | 布乐迪忙碌屋，链接/SPU 515 |
| 发现的问题 | 要解决的经营异常，不只是一个标签 | 上月经营准利润率低于止损线，仍有推广支出 |
| 关键依据 | 触发规则的数据、周期、阈值和对比关系 | 经营准利润率 3.2%，大爆款止损线为 5%，数据期间为上一个完整自然月 |
| 推荐动作 | 可由对应角色执行的动作 | 减少或停止该 SPU 整体推广，同时禁止补货 |

建议还应包含：

- 商品类型；
- 主动作与补货动作；
- 建议优先级；
- 触发的规则编号或规则说明；
- 执行角色；
- 审核、执行与结果状态；
- 导入批次、数据期间和生成时间。

## 9. 建议排序

默认按以下顺序排列行动清单：

1. 清仓。
2. 止损。
3. 品退观察。
4. 加投。
5. 补货。

同一动作内，默认按预计影响大小排序；首版可使用可解释的代理指标，例如经营准利润绝对值、推广费用、库存金额或销售额。若相应指标缺失，保留动作优先级，不进行额外估算。

## 10. 审核、执行与结果跟踪

### 10.1 建议状态

```text
待审核 → 已通过/已驳回 → 待执行 → 已执行 → 已记录结果
```

- 运营主管可通过或驳回建议，并填写备注。
- 建议通过后，按动作类型分配给运营或采购计划。
- 执行人可记录执行时间、执行备注和结果状态。
- 已驳回建议保留原始规则、原始数据和驳回原因，不从历史中删除。

### 10.2 执行责任

| 动作 | 执行人 |
|---|---|
| 加投 | 运营 |
| SPU 整体推广止损 | 运营 |
| 清仓 | 运营 |
| 补货 | 采购计划 |
| 建议审核 | 运营主管 |

## 11. 功能需求

| ID | 功能 | 首版要求 |
|---|---|---|
| F01 | 数据导入与校验 | 导入数据支持部门提供的 SPU 经营表；校验必需字段、唯一 SPU、数据期间、数值类型和日期可解析性 |
| F02 | SPU 经营指标计算 | 读取上一个完整自然月销售额和经营准利润率；在数据存在时计算最近 7 天品退率及库存可售天数 |
| F03 | 固定规则决策 | 按新品、大爆款、小爆款、淘汰商品规则输出主动作，应用动作优先级和补货冲突规则 |
| F04 | AI 建议解释 | 将固定规则结论整理成“具体对象、发现问题、关键依据、推荐动作”；AI 不得修改规则结论 |
| F05 | 行动清单 | 每个导入批次生成一份清单，支持按动作、店铺、运营、审核状态和执行状态查看 |
| F06 | 审核与执行跟踪 | 支持运营主管审核，运营/采购计划更新执行和结果状态，保留历史记录 |
| F07 | 权限隔离 | 运营与运营主管可查看完整信息；采购计划只查看补货/禁止补货结论及必要库存、销量依据 |
| F08 | 规则与数据溯源 | 每条建议保留导入批次、数据期间、触发规则、原始关键值、生成时间及后续状态变更记录 |

## 12. 数据异常与降级规则

| 异常 | 系统行为 |
|---|---|
| SPU ID 缺失或重复 | 该行不进入计算，输出明确错误位置 |
| 上架日期缺失或格式错误 | 不分类、不生成经营动作，标记待修正 |
| 净销售额或经营准利润率缺失 | 不生成利润相关动作，标记待补数 |
| 最近 7 天品退数据缺失 | 不触发品退观察；其他利润动作可继续计算，建议标记“品退数据未校验” |
| 库存或最近 14 天销量缺失 | 不生成补货建议；若主动作为止损/清仓，仍输出“禁止补货” |
| 表头合计与明细不一致 | 不使用表头合计，以通过校验的 SPU 明细行重新汇总 |
| LiteLLM 不可用 | 保留固定规则结论与结构化依据；AI 解释标记生成失败，不伪造解释 |

## 13. AI 与 LiteLLM 边界

### 13.1 AI 职责

- 把规则结论改写成运营可读语言。
- 总结异常、强调超出阈值的关键依据。
- 在不改变主动作的前提下，提供价格、内容或详情页方向的优化提示。
- 帮助生成建议优先级解释。

### 13.2 AI 禁止事项

- 不修改商品类型、利润阈值、品退阈值或动作优先级。
- 不在缺失字段时猜测销售、利润、品退或库存数据。
- 不自动对外部系统发起加投、停投、采购或清仓操作。

### 13.3 LiteLLM 配置

- 使用现有 LiteLLM 网关服务。
- 运维人员通过系统级部署密钥配置。
- 密钥作用于本产品环境，普通用户不可查看。
- 运维负责更新、轮换和失效处理。
- 首版不建设密钥管理页面。

## 14. 首轮验收标准

### 14.1 数据导入

- 可选择玩具事业部并导入 10—20 个真实 SPU。
- 系统能识别必需字段缺失、SPU 重复、日期无法解析和数值异常。
- 首批样本的销售、利润和费用期间按 2026-06-01 至 2026-06-30 处理。

### 14.2 问题与建议

- 至少识别 3 个由真实数据触发的经营问题。
- 每条建议必须包含具体对象、发现问题、关键依据和推荐动作。
- 所有动作结论均能追溯到固定规则和原始关键数据。
- 清仓、止损、观察和加投不得同时作为同一 SPU 的主动作。
- 止损或清仓结论必须同步输出禁止补货。
- 运营确认问题和建议可用于首轮业务评审。

### 14.3 轻闭环

- 运营主管可完成通过或驳回。
- 运营可更新加投、推广止损和清仓的执行状态。
- 采购计划可查看其权限范围内的补货/禁止补货建议并更新执行状态。
- 系统保留审核、执行、结果与备注记录。

## 15. 已知数据限制

1. 现有 `商品链接.xlsx` 包含 10 个真实 SPU 和链接级销售、成本、推广、利润、退款和品退字段。
2. 现有文件没有 SPU 仓内库存、在途库存和最近 14 天销量，因此用该文件试跑时不输出自动补货建议。
3. 表内品退率的实际统计期间尚未被证明为最近 7 天；试跑时应标注“品退口径待校验”，不把该字段作为唯一止损依据。
4. 第 1 行合计与 10 条可见明细不一致；系统忽略源表合计，只处理通过校验的 SPU 明细。
5. 部分上架日期存在混合格式或错位值；无法解析的 SPU 不生成自动决策。
6. 当前没有评价明细、退款/退货原因明细或广告明细，不输出相应的归因和明细级动作。

## 16. 风险与缓解

| 风险 | 失败表现 | 缓解方式 |
|---|---|---|
| 数据期间错标 | 把月度利润误当周利润，导致错误动作 | 导入时要求明确数据期间；建议中固定展示期间；首批数据统一按 2026 年 6 月处理 |
| 上架日期错位 | 新品被判为淘汰商品，或成熟商品被当作新品 | 日期不可解析时不做决策，不使用默认日期猜测 |
| 库存数据缺失 | 系统在不知道库存的情况下给出补货，放大滞销 | 库存字段缺失时禁止生成补货建议；止损/清仓仍可触发禁止补货 |
| 将 AI 输出当作规则结论 | 模型漂移导致同数据不同动作 | 动作必须由固定规则引擎生成；AI 只能解释和排序；页面展示触发规则 |
| 运营止损但采购继续补货 | 重复 515 案例的跨部门断点 | 止损/清仓强制同步禁止补货；采购计划可见结论并更新状态 |
| 建议粒度超出数据能力 | 在没有广告明细时伪造关键词或素材级动作 | 建议只到 SPU 整体粒度；清晰标记无法定位的明细对象 |

## 17. 后续版本候选项
