## P0

### D-P0-01 · 首次绑定必需展示的秘密被全局约束禁止进入页面和响应 `[已关闭]`

- 证据：`PRD详细版.md:1322` 规定 TOTP 密钥和恢复码不出现在页面回显；`requirements.md:1190-1196` 的 NFR-007 又规定 TOTP、恢复码不进入响应。但 `PRD详细版.md:1341-1343` 要求初始化页展示 TOTP 二维码/手工密钥和单次恢复码，`PRD详细版.md:1448` 还要求无二维码时手工录入密钥；AC-F09-01、AC-F09-05 也以保存新恢复码为完成前提。
- 用户后果：按页面流程实现会违反 NFR；按 NFR 字面实现则唯一 Admin 无法绑定验证器、保存恢复码，初始化和两级恢复都无法完成。
- 必须修正：PRD 与 requirements 必须统一区分“生成当次、受保护绑定步骤中的一次性展示”与“后续回显、普通响应、前端包、日志、浏览器持久存储”。明确哪些秘密允许在何时向哪一名操作者展示、何时永久不可再次展示；同步修订 NFR-007、§5.10、§12.6 及对应 AC，不能留给设计自行解释。
- 处置结果：已按上述要求统一，闭环证据见“定点复核处置”表。

### D-P0-02 · “配置冲突”有进入和退出状态，却没有任何可执行的冲突处理动作 `[已关闭]`

- 证据：`PRD详细版.md:1483` 要求冲突用户进入配置冲突页；`PRD详细版.md:1909-1923` 定义配置冲突可回到四种状态；`PRD详细版.md:2047` 写“管理员消除冲突”。但 FR-9.5 的可执行动作只有新增、变更、停用、恢复，界面元素和异常场景均未定义双映射、企业作用域或身份事实冲突由谁在何处查看、选择什么动作、如何确认以及成功后落到哪一状态；`requirements.md:1069-1089` 也只定义拒绝授权，没有冲突解除契约。
- 用户后果：一旦真实身份进入配置冲突，用户只能看到状态页，Admin 也没有产品内可执行路径，系统重新出现本次 F09 要消除的登录死路。
- 必须修正：为已列出的每一种冲突给出唯一责任路径和可观察结果；若某类冲突明确只能由运维在产品外修复，也必须在用户页和 Admin 详情中给出具体责任岗位、联系方式、刷新/重试条件及冲突解除后的状态投影。不得借此扩成通用身份合并或目录治理。
- 处置结果：产品内双映射与权威身份源冲突已分流并各有唯一下一步，闭环证据见“定点复核处置”表。

## P1

### D-P1-01 · 部署恢复通知失败后没有可达的处置与补偿闭环 `[已关闭]`

- 证据：`PRD详细版.md:1428` 在恢复表面定义四个通知状态，`PRD详细版.md:1447` 声称存在告警和补偿入口；但 `PRD详细版.md:1562` 的 Admin 导航只有待处理、身份、审计和安全设置，没有恢复通知任务或补偿入口，文档也没有说明恢复页跳转正式登录后由谁、从哪里再次找到失败任务、提交线下证据或确认闭环。`requirements.md:1036-1045` 只要求独立追踪结果，没有补足可达性。
- 用户后果：凭据已安全换新后，页面可能离开恢复现场；通知失败任务无人可见、无人能完成补偿，产品却把非静默通知列为 MVP 和上线门禁。
- 必须修正：固定通知状态的查看者、入口、离开恢复页后的返回路径、失败时唯一下一步、补偿证据提交/确认责任及完成反馈；可以复用安全设置或审计详情，但必须有明确可达路径，不必新增通用通知中心。
- 处置结果：已复用安全设置和审计详情形成返回、重试、补偿与确认路径，闭环证据见“定点复核处置”表。

### D-P1-02 · 部署恢复的实际操作者与新凭据持有人没有统一 `[已关闭]`

- 证据：`requirements.md:1043` 写“恢复执行人提供部署恢复材料并完成新密码和 TOTP 设置”；`PRD详细版.md:249-250` 将运维定义为恢复执行岗位，同时又要求唯一 Admin 本人保管 TOTP 和恢复材料；`PRD详细版.md:1437` 强调独立审批人、恢复执行人和证据，但没有说明 Admin 持有人何时进入流程、谁能看见新 TOTP 密钥/恢复码、交接时如何避免运维获得可长期登录的完整凭据。
- 用户后果：设计可能让运维绑定自己的验证器或看到 Admin 的长期恢复材料，也可能要求已失去凭据的 Admin 独自执行其无法进入的步骤；两种实现都破坏角色责任或使恢复无法完成。
- 必须修正：统一部署恢复各步骤的参与者和权限呈现，至少明确恢复执行人、Admin 持有人、通知接收人分别能看到和提交什么，以及新长期凭据最终只归谁保管。该修正是现有双人恢复边界的落图，不是新增角色。
- 处置结果：恢复执行人只开启一次性交接，长期凭据仅由 Admin 持有人设置和当次查看，闭环证据见“定点复核处置”表。

### D-P1-03 · “已配置待重新登录”页面缺少契约要求的目标角色呈现 `[已关闭]`

- 证据：`requirements.md:1058-1067` 与 `PRD详细版.md:2727-2733` 要求配置成功后显示唯一目标角色；但 FR-9.4 的用户状态页元素表（`PRD详细版.md:1464-1475`）只有状态、时间、责任信息、下一步和重新登录按钮，没有目标角色、对应工作台或角色变更后的前后差异展示规则。
- 用户后果：用户在重新登录前无法核对自己将以运营还是运营主管进入系统；配置错误只能在进入工作台后才被发现，削弱“零错授”的最后一道用户可见确认。
- 必须修正：在“已配置待重新登录”状态明确展示唯一目标角色和重新登录后的目标工作台；对角色变更/恢复说明当前旧会话已失效。不得允许用户自行改选角色。
- 处置结果：状态页、AC 和机器契约均已补齐唯一目标角色、对应工作台、旧会话失效及禁止改选，闭环证据见“定点复核处置”表。

## P2

### D-P2-01 · 身份检索和待处理/审计列表缺少完整的加载、空结果与筛选失败状态

- 证据：FR-9.4、FR-9.5、FR-9.6 定义分页列表、筛选和检索，但只明确网络失败可重试；没有区分“系统确实没有记录”“当前筛选无结果”“身份属性暂不可取”“页面仍在加载”。F01—F08 已明确禁止把加载失败显示为空清单，F09 未继承同等口径。
- 用户后果：Admin 可能把加载失败误认为没有待处理用户，或在搜索无结果时不知道应修改条件还是等待外部身份数据恢复。
- 建议：设计阶段为三类列表统一初始加载、真实空状态、筛选无结果、加载失败和刷新后状态；不增加目录浏览或批量能力。

### D-P2-02 · 机器状态码与用户文案混在同一展示定义中

- 证据：`PRD详细版.md:1428`、`PRD详细版.md:1890-1895`、`PRD详细版.md:2751` 直接把 `pending_delivery`、`failed_pending_compensation` 等内部枚举写进页面状态。
- 用户后果：实现可能直接暴露英文状态码，也可能由不同页面各自翻译，造成恢复页、审计和告警文案不一致。
- 建议：保留稳定机器枚举作为数据值，同时只规定一套面向操作者的中文主文案、解释和下一步；技术码仅在有权限的诊断/审计语境按需展示。

### D-P2-03 · 角色或版本冲突后的长表单恢复体验未定义

- 证据：FR-9.5 要求填写审批人、时间、证据类型/引用、核验结果和高风险确认；并发冲突时只写“显示最新状态”，未说明非敏感已填内容是否保留、哪些字段必须重新核验、旧确认是否失效。
- 用户后果：Admin 可能因版本冲突丢失整份审批录入，或页面保留已过时的目标角色与影响摘要后再次提交。
- 建议：设计阶段明确冲突后保留非敏感草稿、强制刷新身份/角色版本并重新确认影响摘要；秘密字段和已失效确认不得保留。

### D-P2-04 · 安全关键表单没有最低可访问性要求

- 证据：PRD 只确认 PC 1280—1440px、窄屏折行和二维码失败时手工密钥，没有规定键盘焦点顺序、字段错误与控件关联、冷却倒计时的非视觉提示、二维码的等价文本入口、状态不只依赖颜色。
- 用户后果：键盘用户或视觉能力受限的操作者可能无法完成初始化、恢复和高风险确认；错误状态即使存在，也可能无法被辅助技术识别。
- 建议：后续设计至少覆盖表单标签/错误关联、焦点回收、键盘操作、非颜色状态表达、倒计时可感知更新和二维码等价手工路径；不扩大到移动端业务操作。

## 已通过的设计检查

- 用户旅程：正常路径已覆盖 setup → 正式 Admin 登录、钉钉无角色 → 待处理 → 配置 → 重新登录，以及既有授权用户直达原工作台。
- 状态反馈：初始化/登录/两级恢复具备初始、校验、提交、成功、冷却、失败和结果未知；五态明确是展示投影，不作为业务鉴权源。
- 权限呈现：Admin 与业务导航、Cookie、错误响应和数据权限分离；Admin 默认无经营权限，已有业务用户不因 F09 管理面故障被阻塞。
- 范围可用性：已有授权/停用身份可通过最小列表或单人检索进入统一详情；首版仍保持单 Admin、双固定业务角色、单人操作和非通用 IAM 边界。
- 错误恢复：网络结果未知采用真实状态查询而非盲目重放；旧会话、旧恢复材料和失败事务的用户可见结果总体一致，通知外部失败不回滚已经安全完成的凭据恢复。
